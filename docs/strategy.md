# Стратегия и видение (набросок)

- **Date:** 2026-09-24
- **Updated:** 2026-09-24

Это **не решение** и не план. Это набросок мыслей о том,
куда проект может развиваться. Возвращаться к нему —
при подходе к Этапу 4 (веб, БД, Docker) и Этапу 5 (UI).

## Контекст

Проект вырос как инструмент для одного пользователя
с ручным конфигом (`settings.yaml`) и запуском через systemd.
Сейчас работает для MAX, в планах — VK и другие каналы.

Целевая аудитория (гипотеза на 2026-09): **технически
неграмотные владельцы ресурсов** — люди, которые ведут
WP-сайт (например, районная газета, небольшой блог),
но не готовы возиться с YAML, Docker и systemd. Их много.

## Возможное развитие

Две возможные формы продукта:

### Продукт A. Консольный (текущий)

- Один пользователь, один инстанс.
- Ручной `settings.yaml`, `.env`.
- Запуск в systemd.
- Открытый исходник, self-hosted.
- Аудитория: технически подкованные.

### Продукт B. Веб-версия с пользователями

- Мультипользовательская.
- Регистрация, кабинеты, БД.
- Веб-интерфейс для настройки.
- Хостинг, домены, биллинг (?), техподдержка.
- Аудитория: технически неграмотные владельцы ресурсов.

## Стратегический выбор

**Не разделять, а развивать A, оставив возможность для B.**

Причины:

1. **A — реальная ценность сейчас.** B — гипотеза.
2. **Ядро уже отделено** (ADR 0020, ADR 0030). Парсер,
   трансформер, экспортер — независимые модули. Если B
   понадобится, ядро переиспользуется.
3. **B — не «ещё немного кода»**, а другой продукт: веб,
   аутентификация, БД, миграции, деплой. Месяцы работы
   и годы поддержки.
4. **Сигнал для B — реальные запросы.** Если появятся issues
   «а можно без YAML?», «а можно зарегистрироваться?» —
   это сигнал. Пока таких нет.

## Промежуточные шаги (между A и B)

Не требуют SaaS, но улучшают UX:

1. **CLI-визард настройки.** `wp-reposter init` — генерирует
   `settings.yaml` из ответов на вопросы.
2. **Локальный веб-интерфейс.** `wp-reposter web` — сервер
   на `localhost:8080`, редактирование конфига в браузере.
   Без пользователей, без БД, один инстанс.
3. **Docker-образ.** Проще для деплоя (планируется в Этапе 4).

## Мотивация (зачем B)

- **Деньги.** SaaS с подпиской. Не ради заметного дохода,
  а как опыт монетизации.
- **Помочь другим.** Целевая аудитория — технически
  неграмотные владельцы ресурсов.
- **Интерес.** Мультипользовательские системы — привычная
  автору область.

## Юридические вопросы для B

- Токены каналов — **чувствительные данные**.
  Даже если нет ФИО, есть идентификатор канала и токен доступа.
  Это уже риск утечки.
- Возможно, попадает под 152-ФЗ (РФ) и/или GDPR (ЕС).
  Точная юрисдикция — по месту хостинга.
- Нужны: политика конфиденциальности, шифрование токенов,
  безопасное хранение, удаление по запросу.
- Практика: 152-ФЗ — полезный опыт, даже если проект
  не выйдет на массовый рынок.

## Когда возвращаться

- При подходе к **Этапу 4** (веб, БД, Docker) — понять,
  нужна ли мультипользовательность.
- При появлении **первых внешних запросов** на удобство
  (issues, письма).
- При **желании начать монетизацию** — считать экономику.

## Что НЕ решаем сейчас

- Нужен ли SaaS.
- Нужна ли мультипользовательность.
- Нужен ли веб-интерфейс (локальный или хостинговый).
- Лицензионная модель (MIT сейчас, что дальше).
