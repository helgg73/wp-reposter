# ADR 0009: Хранение состояния — JSON-файл

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0007 (cutoff_date), ADR 0010 (лимит постов)

## Context

Необходимо хранить информацию об отправленных постах (GUID, message_id, дата) для предотвращения дублирования. Рассматривались JSON-файл, SQLite и PostgreSQL.

Прямые альтернативы:

1. **JSON-файл** — просто, прозрачно, нулевая настройка.
2. **SQLite** — избыточно для одного источника, сложнее отлаживать.
3. **PostgreSQL** — требует СУБД, избыточно для Этапа 1.
4. **Redis** — требует отдельного сервиса.

## Decision

Использовать **JSON-файл** (`data/state.json`) для локальной разработки.

Реализация:

- **Модуль:** `src/state.py` → `StateManager`
- **Файл:** `data/state.json` (создаётся через `Path.mkdir(parents=True, exist_ok=True)`)
- **Структура:**
  ```json
  {
    "processed_posts": {
      "<guid>": {"message_id": "...", "sent_at": "...", "channel": "max"}
    },
    "last_processed_date": "..."
  }

##   Consequences

**Положительные:**

- Нулевая настройка — просто файл.
- Прозрачность — можно открыть и посмотреть содержимое.
- Легко отлаживать — не нужен клиент СУБД.
- Легкая миграция на БД в будущем.
- Достаточно для одного источника и локального запуска.

**Отрицательные:**

- Не подходит для многопользовательской системы (Этап 4+).
- Нет транзакций — риск повреждения при одновременной записи.
- _save() вызывается на каждый mark_processed() — при 5 постах 5 записей файла. Батчинг отложен до Этапа 2 (принято как допущение).

**Что теперь нельзя / не нужно:**

- Не нужно ставить СУБД для локального запуска.
- Не нужно писать SQL-запросы.
- Не нужно мигрировать на PostgreSQL до Этапа 4.
