===== 0001-project-dump-for-llm-context.md =====
# ADR 0001: Дамп репозитория в один файл для LLM

- **Status:** Accepted
- **Date:** 2026-09-15

## Context

При работе с LLM (ChatGPT, Claude, локальные модели) над проектом
возникает задача передать модели контекст: структуру и содержимое
кода. Ручное копирование файлов в чат — медленно, ведёт к пропускам
и не воспроизводится.

Прямые альтернативы:

1. **Готовые инструменты** (Repomix, code2prompt, Gitingest) —
   зрелые, но тянут зависимости (Node.js, Rust), избыточны для
   небольших проектов, и часть из них отправляет код на свои серверы.
2. **Ручной сбор** — не масштабируется, легко забыть файл.
3. **MCP-серверы** — требуют настройки клиента, привязывают к
   конкретному инструменту (Claude Desktop, Cursor).

Контекстное окно LLM также накладывает ограничение: дамп должен
быть предсказуем по объёму, чтобы не улететь в «жёлтую зону»
деградации качества (>50–80k токенов).

Проект современный, все файлы в UTF-8. Поддержка legacy-кодировок
(Windows-1251, UTF-16) — лишняя сложность для инструмента,
рассчитанного на небольшие актуальные репозитории.

Отдельный риск: случайно закоммиченный `.env` или `credentials.json`
попадёт в дамп и уйдёт в облачную LLM. Это не гипотетический сценарий:
коммит `.env` — одна из самых частых ошибок в небольших проектах,
где нет pre-commit-хуков и review-процесса. Утечка необратима:
даже если потом удалить файл из репозитория и перегенерировать дамп,
содержимое остаётся в истории чата с моделью.

## Decision

Написан собственный скрипт `project_dump.py`, который:

- запускается из корня репозитория;
- использует `git ls-files` для получения списка отслеживаемых
  файлов — так `.gitignore`, вложенные `.gitignore` и глобальный
  `~/.gitignore` работают автоматически, без парсинга своими руками;
- пропускает бинарные файлы (эвристика по NUL-байту в первых 8 KB;
  ложные срабатывания на UTF-16 — см. Consequences);
- пропускает lock-файлы и сгенерированный код через `EXCLUDE_PATTERNS`;
- пропускает Markdown-файлы (`*.md`) — документация полезна человеку,
  но в дампе кода для LLM она только занимает токены. При
  необходимости конкретный `.md` можно вернуть в дамп через
  добавление в `ALLOW_PATTERNS`;
- нормализует переносы строк к `\n` при чтении: файлы с CRLF
  (Windows-переносы) в дампе выглядят единообразно, без лишних
  `\r`, которые редакторы отображают как пустые строки;
- исключает из дампа потенциальные секреты: `.env`, ключи и
  сертификаты (`*.key`, `*.pem`, `*.p12`), `credentials.*`,
  `secrets.*`, SSH-ключи, конфиги облачных сервисов;
- эвристика «похоже на секрет» проверяет имя файла по подстрокам
  (`secret`, `password`, `credential`, `token`, `apikey`, `api_key`,
  `private`). Hint `auth` исключён из списка: он даёт массовые
  ложные срабатывания на документации (`AUTHORS`, `authentication.md`,
  `authorization.md`). Файлы вида `auth.json` с токенами эвристикой
  не ловятся — это осознанный компромисс;
- сравнивает имена файлов с паттернами регистронезависимо и
  кроссплатформенно: `*.KEY`, `*.key`, `Private.Key` отсеиваются
  одинаково на Windows и Linux. Реализовано через `fnmatchcase`
  с ручной нормализацией регистра;
- сохраняет в дампе шаблоны `.env` без реальных секретов
  (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`):
  они полезны, чтобы LLM видел ожидаемые переменные окружения.
  Реализовано через allow-list, который проверяется после
  пользовательских `-x`, но до встроенных `EXCLUDE_PATTERNS`;
- пишет результат в `project_dump.txt` с оглавлением в начале
  и заголовками `===== path =====` перед каждым файлом;
- печатает предварительную оценку объёма в байтах и токенах до
  записи, предупреждает при превышении порога;
- поддерживает флаги:
  - `-o` — имя выходного файла;
  - `-x` / `--exclude` — дополнительный glob-паттерн исключения;
  - `--no-toc` — отключить оглавление;
  - `--max-bytes` — прервать при превышении лимита;
  - `--no-default-excludes` — не применять встроенные исключения
    (для отладки или если фильтрация не нужна);
  - `--force` — продолжить, несмотря на найденные подозрительные файлы;
- использует коды возврата: 0 — успех, 1 — ошибка git, 2 — превышен
  `--max-bytes`, 3 — нечего дампить, 4 — найдены файлы, похожие
  на секреты (нужен `--force`).

Скрипт остаётся одним файлом без внешних зависимостей (только
стандартная библиотека). Это осознанный выбор в пользу простоты
для небольших проектов.

## Consequences

**Положительные:**

- Воспроизводимость: один и тот же дамп получается на любой машине
  с тем же набором закоммиченных файлов.
- Кроссплатформенная воспроизводимость: одинаковые правила
  сравнения имён файлов на Windows и Linux, дампы совпадают
  по составу независимо от ОС.
- Дамп в LF независимо от исходных переносов: результат
  воспроизводим между Windows и Linux, редакторы не показывают
  «фантомных» пустых строк.
- Пустой результат (все файлы отфильтрованы) не создаёт файл
  и завершается с кодом 3 — защита от случайной передачи пустого
  дампа в LLM.
- Нулевые зависимости: работает на голом Python 3.9+.
  Более старые версии (включая 3.5) не поддерживаются из-за
  f-strings, `subprocess.run(capture_output=...)` и PEP 585-аннотаций
  (`list[str]`, `dict[str, int]`).
- Прозрачность: скрипт читается за 5 минут, все настройки в шапке.
- Контроль объёма: оценка токенов до записи, `--max-bytes`,
  `-x` / `--exclude`.
- Защита от случайной утечки секретов: подозрительные файлы
  блокируют запись дампа до явного подтверждения через `--force`.
- Шаблоны `.env.example` остаются в дампе, давая LLM контекст
  о переменных окружения проекта.

**Отрицательные:**

- Не масштабируется на очень большие проекты: полный дамп может
  не влезть в контекст, придётся дампить поддеревья вручную.
- Оценка токенов грубая (`bytes / 4`), погрешность ±20%.
- `git ls-files --cached` не видит неотслеживаемые файлы, что
  обычно правильно, но требует `git add` для новых файлов.
- Нет автоматической интеграции с LLM-клиентами (в отличие от
  MCP-серверов), каждый раз нужно копировать результат в чат.
- Не поддерживаются файлы в кодировках, отличных от UTF-8:
  Windows-1251 и подобные не отсеиваются эвристикой бинарности
  (NUL-байта в них нет) и попадают в дамп с заглушками `�`.
  Скрипт предупреждает об этом в stderr с указанием файла и
  позиции ошибки, но не блокирует запись.
- Эвристика бинарности (поиск NUL-байта) ложно срабатывает на
  UTF-16: такие файлы будут пропущены как бинарные. Для
  UTF-8-проектов это не проблема, для смешанных — потребуется
  доработка.
- Защита от секретов работает только по имени файла. Файлы с
  нейтральным именем (`config.yaml`) или с `auth` в имени
  (`auth.json`), содержащие ключи или пароли, в дамп попадут.
  Проверка содержимого на паттерны (`AKIA...`,
  `-----BEGIN PRIVATE KEY-----` и т.п.) в текущем решении
  не реализована.
- Эвристика «похоже на секрет» может давать ложные срабатывания
  на файлах с `token`, `password`, `credential`, `private` в имени
  (например, `tokenizer.md`, `password_policy.yaml`). Лечится
  флагом `--force` или добавлением в `-x`.
- Allow-list шаблонов `.env` может устареть: если в проекте
  появится новый формат шаблона (например, `.env.local.example`),
  его нужно добавить в `ALLOW_PATTERNS`. Пользователь может
  явно исключить шаблон через `-x`, если он не нужен.

**Что теперь нельзя / не нужно:**

- Не нужно парсить `.gitignore` самостоятельно — git делает это
  лучше.
- Вывод `project_dump.txt` прописан в `.gitignore`, поэтому git
  его не отслеживает. Это даёт две вещи: файл не попадёт в коммит
  случайно, и `git ls-files` его не вернёт, то есть в сам дамп он
  тоже не попадёт — без дополнительных исключений в скрипте.

# ADR 0002: Менеджер пакетов — uv

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0003 (ruff), ADR 0012 (единый источник моделей)

## Context

Нужен современный менеджер пакетов для Python-проекта: lock-файлы, группы зависимостей (dev/prod), быстрая установка, нативная поддержка Windows, лёгкая интеграция с Docker.

Прямые альтернативы:

1. **pip + requirements.txt** — стандарт де-факто, но нет lock-файлов, нет групп зависимостей, медленная установка.
2. **Poetry** — зрелый, но медленнее, свой DSL для конфигов (`[tool.poetry]`), тяжелее для Docker-образов.
3. **PDM** — менее зрелый, меньше комьюнити.

## Decision

Использовать **uv** от Astral.

Реализация:

- **Файл:** `pyproject.toml`
- **Секции:** `[project].dependencies`, `[dependency-groups].dev`
- **Ключевые поля:**
  - `requires-python = ">=3.12"`
  - Зависимости: `httpx>=0.27.0`, `pydantic>=2.7.0`, `pydantic-settings>=2.2.0`, `pyyaml>=6.0.1`, `maxapi>=1.2.0`
  - Dev-группа: `pytest>=8.2.0`, `pytest-asyncio>=0.23.6`, `respx>=0.21.0`, `ruff>=0.4.0`
- **Lock-файл:** `uv.lock` — в репозитории есть. **Осознанно не включается в дамп TOC** (см. ADR 0001: `EXCLUDE_PATTERNS` пропускает lock-файлы, чтобы не раздувать дамп).

## Consequences

**Положительные:**

- Скорость установки в 10–100 раз выше pip/poetry (написан на Rust).
- Детерминированные сборки через `uv.lock`.
- Группы зависимостей без дополнительного DSL.
- Полная совместимость с pip-экосистемой.
- Нативная поддержка Windows.
- Лёгкие Docker-образы на Этапе 4.

**Отрицательные:**

- Экосистема менее зрелая, чем у poetry (но быстро развивается).
- `uv.lock` не виден в дампе TOC — LLM не сможет увидеть точные зафиксированные версии. При необходимости можно передать `uv.lock` в чат отдельно.

**Что теперь нельзя / не нужно:**

- Не нужно вести `requirements.txt` параллельно — источник истины один, `pyproject.toml`.
- Не нужно парсить `pyproject.toml` вручную для установки — uv делает это сам.
- Не нужно добавлять `uv.lock` в дамп TOC — это осознанное решение (см. ADR 0001).

# ADR 0003: Линтинг и форматирование — ruff

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0002 (uv), ADR 0005 (asyncio)

## Context

Нужен инструмент для статического анализа и форматирования кода. Классический набор — black + flake8 + isort. Альтернатива — один инструмент.

Прямые альтернативы:

1. **black + flake8 + isort** — три инструмента, три конфига, три вызова в CI, медленнее.
2. **pylint** — медленный, сложная настройка, не форматирует.
3. **ruff** — один инструмент на Rust, совместим с black.

## Decision

Использовать **ruff** для линтинга и форматирования.

Реализация:

- **Файл:** `pyproject.toml`
- **Секции:** `[tool.ruff]`, `[tool.ruff.lint]`, `[tool.ruff.lint.isort]`
- **Ключевые поля:**
  - `target-version = "py312"` — синхронизировано с `requires-python = ">=3.12"` (см. ADR 0002)
  - `line-length = 100`
  - `select = ["E", "W", "F", "I", "UP", "B", "SIM"]`
  - `ignore = ["E501"]` — длину строк контролирует `ruff format`
  - `known-first-party = ["src"]`

## Consequences

**Положительные:**

- Один инструмент вместо трёх.
- Скорость в 10–100 раз выше (Rust).
- Совместимость с black на 99%.
- Встроенный pyupgrade (правила `UP`) — автообновление синтаксиса.
- Активное развитие и большое сообщество.

**Отрицательные:**

- Некоторые правила требуют ручной настройки (например, UP015).
- `target-version` и `requires-python` — два места, где указана версия Python. Их нужно держать синхронно вручную.

**Что теперь нельзя / не нужно:**

- Не нужно ставить black, flake8, isort отдельно.
- Не нужно держать `.flake8`, `setup.cfg`, `.isort.cfg` — всё в `pyproject.toml`.
===== 0004-adr-wordpress-rest-api.md =====
# ADR 0004: Источник данных — WordPress REST API вместо RSS

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0007 (cutoff_date), ADR 0013 (синхронный парсер)

## Context

Изначально планировался парсинг RSS-ленты WordPress. Но RSS:

- не отдаёт featured images (только `<enclosure>`, если повезёт);
- требует сложного парсинга HTML из `<description>`;
- не поддерживает серверную фильтрацию по категориям и тегам;
- отдаёт XML, который нужно парсить.

WordPress REST API (`/wp-json/wp/v2/posts`) — встроен в ядро WP, отдаёт JSON, поддерживает `_embed`, `categories`, `after`.

Прямые альтернативы:

1. **RSS + парсинг HTML** — нет featured images, сложный парсинг, нет серверной фильтрации.
2. **WP XML-RPC** — устаревший протокол, ограниченный функционал.
3. **Скрейпинг HTML** — хрупко, ломается при изменении вёрстки.
4. **WP REST API** — встроен, JSON, `_embed`, серверная фильтрация.

Риск: не все WP-сайты держат REST API открытым. Но для новостных сайтов это обычно так.

## Decision

Использовать **WordPress REST API** (`/wp-json/wp/v2/posts`).

Реализация:

- **Модуль:** `src/parser.py`
- **Класс:** `WordPressParser`
- **Методы:**
  - `__init__()` — формирует `self.api_url = f"{base_url}{source.api_path}"`
  - `fetch_posts()` — GET `/posts` с параметрами `_embed`, `orderby=date`, `order=desc`, `per_page`, `page`, `after`, `categories`
  - `_extract_image()` — извлекает URL из `_embedded["wp:featuredmedia"][0]["media_details"]["sizes"][featured_image_size]`, с fallback на первый доступный размер
  - `_should_exclude()` — фильтрация по `_embedded["wp:term"]` (категории — `terms[0]`, теги — `terms[1]`)
  - `_format_post()` — преобразует ответ API во внутренний формат `{id, link, title, content, published, _image_url}`
  - `_clean_text()` — очистка HTML и сущностей
- **Конфиг источника:** `src/models.py` → `SourceConfig`
  - `base_url`, `api_path = "/wp-json/wp/v2"`
  - `featured_image_size = "medium"`
  - `max_pages = 3`, `per_page = 20`
  - `include_category_ids`, `exclude_category_ids`, `include_tag_ids`, `exclude_tag_ids`

## Consequences

**Положительные:**

- Featured images с размерами (`thumbnail`, `medium`, `large`) из коробки.
- Серверная фильтрация по категориям — меньше трафика.
- Чистый JSON вместо XML + HTML.
- `_embed` для получения связанных данных одним запросом.
- Пагинация через `?page=N&per_page=20`.

**Отрицательные:**

- Требует доступа к WP REST API. Если сайт отключил REST API — не работает.
- `_should_exclude()` жёстко привязан к порядку `wp:term[0]` / `wp:term[1]`. Если WP вернёт термы в другом порядке — сломается. На Этапе 2 нужно уточнить (см. план правок).
- `_extract_image()` делает fallback на первый доступный размер, если запрошенного нет. Это может привести к неожиданно большому изображению.

**Что теперь нельзя / не нужно:**

- Не нужно парсить RSS и XML.
- Не нужно чистить HTML от `<description>` — API отдаёт `excerpt.rendered` и `content.rendered`, которые чистит `_clean_text()`.
===== 0005-adr-asyncio-architecture.md =====
# ADR 0005: Асинхронная архитектура на asyncio

- **Status:** Accepted
- **Date:** 2026-09-10
- **Updated:** 2026-09-16
- **Related:** ADR 0004 (WP REST API), ADR 0008 (maxapi), ADR 0013 (синхронный парсер), ADR 0016 (Этап 2)

## Context

Проект должен работать как фоновый сервис с интервалом проверки 5 минут. Рассматривались синхронный цикл с `time.sleep()` и асинхронный подход.

## Decision

Использовать **asyncio** для всей архитектуры.

- `main.py` — асинхронный цикл
- `exporter.py` — async методы
- `state.py` — sync (файловые операции быстрые)
- `parser.py` — **синхронный на Этапе 1** (см. ADR 0013)

## Consequences

**Положительные:**
- Готовность к переходу на FastAPI (Этап 4)
- Корректное завершение по сигналу
- Параллельная обработка нескольких источников (в будущем)

**Отрицательные:**
- Требует понимания async/await от разработчика
- Парсер блокирует event loop на Этапе 1

**Что теперь нельзя:**
- Нельзя использовать `time.sleep()` — только `await asyncio.sleep()`
- Нельзя блокировать event loop долгими операциями

**Следующий шаг:**
- На Этапе 2 (S2-11) парсер будет переведён в async (см. ADR 0016).
- На Этапе 4 — переход на FastAPI (APScheduler в lifespan).
===== 0006-adr-pydantic-settings-secrets.md =====
# ADR 0006: pydantic-settings для секретов

- **Status:** Accepted
- **Date:** 2026-09-10
- **Updated:** 2026-09-16
- **Related:** ADR 0001 (project dump), ADR 0012 (модели), ADR 0018 (Этап 4)

## Context

Токены ботов, ID чатов и другие секреты не должны попадать в публичный репозиторий. Рассматривались хардкод, YAML-конфиги и переменные окружения.

## Decision

Использовать **pydantic-settings** с файлом `.env` для секретов.

- Секреты (токены, ID) — в `.env` (добавлен в `.gitignore`)
- Шаблон `.env.example` — в репозитории (попадает в дамп TOC)
- Публичные настройки (URL, лимиты) — в `config/settings.yaml`

## Consequences

**Положительные:**
- Секреты не попадают в Git
- Единый интерфейс для локальной разработки и продакшена
- Валидация обязательных полей при старте
- `.env.example` виден в дампе TOC (LLM видит шаблон)

**Отрицательные:**

- Нельзя добавлять `.env` в Git
- Нельзя использовать YAML для секретов

**Следующий шаг:**
- S4-05: При развёртывании на `docker_host` — передача секретов через `environment` в compose.
===== 0007-adr-cutoff-date-spam-protection.md =====
# ADR 0007: Защита от спама через cutoff_date

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0010 (лимит постов), ADR 0009 (JSON state)

## Context

При первом запуске API может вернуть 50+ старых постов. Если отправить всё сразу — спам в канале. Если лимитировать отправку, но не сдвигать границу времени — старые посты будут приходить снова и снова.

Прямые альтернативы:

1. **Отправлять всё при первом запуске** — спам.
2. **Хранить все GUID и проверять** — состояние разрастается, логика усложняется.
3. **Лимит без cutoff_date** — старые посты приходят повторно.
4. **cutoff_date с движением вперёд** — простая логика, предсказуемое поведение.

## Decision

Использовать **cutoff_date** (дата отсечки) с движением только вперёд во времени.

Как работает:

1. После первого запуска граница = дата **самого нового** отправленного поста.
2. В следующий раз API возвращает только посты новее (`?after=cutoff_date`).
3. Старые посты игнорируются навсегда.

Реализация:

- **Модуль:** `src/state.py` → `StateManager`
  - Поле `last_processed_date: str | None`
  - `_load()` — читает `last_processed_date` из JSON
  - `_save()` — сохраняет `last_processed_date`
  - `update_cutoff_date(date_str)` — обновляет и сохраняет; докстринг: «Обновляет дату отсечки (самый новый пост, который мы взяли в работу)»
- **Модуль:** `src/parser.py` → `WordPressParser.fetch_posts(cutoff_date)`
  - `if cutoff_date: params["after"] = cutoff_date`
- **Модуль:** `src/main.py` → `check_sources()`
  - `state.last_processed_date` передаётся в `parser.fetch_posts()`
  - `newest_sent_date = entry.get("published")` — берётся первый (самый новый) отправленный пост
  - `state.update_cutoff_date(newest_sent_date)`

## Consequences

**Положительные:**

- Гарантия отсутствия спама устаревшим контентом.
- Предсказуемое поведение при первом запуске.
- Простая логика — движение только вперёд.
- Не нужно хранить все GUID для защиты от повторов — cutoff_date отсекает старые посты на стороне API.

**Отрицательные:**

- Посты, не влезшие в лимит при первом запуске, теряются навсегда (принято как feature).
- Если `published` у поста — не дата, а что-то другое (например, `null`), cutoff_date сломается. Нужно будет уточнить на Этапе 2.

**Что теперь нельзя / не нужно:**

- Не нужно проверять все GUID при каждом запросе — API отдаёт только посты новее cutoff_date.
- Не нужно сдвигать cutoff_date назад — только вперёд.
- Не нужно удалять `last_processed_date` из состояния без явного сброса — иначе вернётся «хвост» старых постов.

# ADR 0008: SDK для MAX — maxapi

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0005 (asyncio), ADR 0011 (disable_link_preview)

## Context

Для отправки сообщений в мессенджер MAX рассматривались прямые HTTP-запросы к API и использование официальной библиотеки maxapi.

Прямые альтернативы:

1. **Прямые HTTP-запросы** — нужно писать клиент вручную, нет типизации, нет обработки ошибок.
2. **Сторонние обёртки** — менее надёжны, чем официальный SDK.
3. **maxapi** — официальная Python-библиотека, Pydantic-модели, загрузка медиа, retries.

## Decision

Использовать **maxapi** (официальная Python-библиотека).

Реализация:

- **Модуль:** `src/exporter.py` → `MaxExporter`
- **Импорты:** `from maxapi import Bot`, `from maxapi.types import InputMediaBuffer`
- **Методы:**
  - `__init__()` — `self.bot = Bot(token=...)` при `config.enabled`
  - `export()` — `await self.bot.upload_media(media)`, `await self.bot.send_message(chat_id, text, attachments, disable_link_preview)`
  - Извлечение ID: `result.message.body.mid` с fallback на `result.id` / `result.message_id`
  - `close()` — `await self.bot.session.close()` или `await self.bot.close()`

## Consequences

**Положительные:**

- Типобезопасность (Pydantic-модели для всех объектов).
- Встроенная поддержка загрузки медиа (`InputMedia`, `InputMediaBuffer`).
- Автоматическая обработка ошибок и retries.
- Поддержка webhook и polling из коробки.
- Активное развитие.

**Отрицательные:**

- Зависимость от третьей стороны (но это официальный SDK).
- Нестандартный путь к ID: `result.message.body.mid` вместо `result.message_id`. Приходится писать fallback.
- `close()` использует внутреннюю `bot.session` — если maxapi изменит API, сломается.

**Что теперь нельзя / не нужно:**

- Не нужно писать HTTP-клиент для MAX вручную.
- Не нужно парсить ответы MAX вручную — maxapi отдаёт Pydantic-модели.
- Не нужно реализовывать retries самостоятельно — maxapi делает это сам.

# ADR 0009: JSON state хранение

- **Status:** Accepted
- **Date:** 2026-09-10
- **Related:** ADR 0005 (asyncio), ADR 0018 (Этап 4)

## Context

Необходимо хранить состояние обработанных постов (GUID, message_id, дата отправки) для предотвращения дублирования при перезапуске.

Варианты:
1. **JSON-файл** (`data/state.json`) — просто, прозрачно, но не масштабируется.
2. **SQLite** — локальная БД, но требует миграций.
3. **PostgreSQL** — продакшен, но требует сервера.

На Этапе 1: один источник, один канал, локальный запуск. JSON достаточно.

## Decision

Использовать JSON-файл `data/state.json` для хранения состояния на Этапе 1.

Структура:
```json
{
  "processed_posts": {
    "guid-123": {
      "message_id": "mid.xxx",
      "sent_at": "2026-09-15T10:30:00",
      "channel": "max"
    }
  },
  "last_processed_date": "2026-09-15T10:30:00"
}
```

**На Этапе 4 (задача S4-02) состояние будет мигрировано на PostgreSQL.** Для локальной разработки останется возможность использовать SQLite через `DATABASE_URL`.

## Consequences

**Положительные:**
- Нулевая настройка (просто файл).
- Прозрачность (можно открыть и посмотреть).
- Легко отлаживать.

**Отрицательные:**
- Не подходит для многопользовательской системы (Этап 4+).
- Нет транзакций (риск повреждения при одновременной записи).
- Нет индексов (медленный поиск при большом количестве записей).

**Что теперь нельзя:**
- Нельзя использовать state.json в FastAPI (Этап 4) без миграции на БД.
- Нельзя запускать несколько инстансов репостера с общим state.json.

**Следующий шаг:**
- S4-02: Миграция на PostgreSQL (Этап 4).

# ADR 0010: Лимит постов за один цикл — max_new_posts_per_run

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0007 (cutoff_date)

## Context

Необходимо ограничить количество постов за один цикл проверки, чтобы не перегружать канал и API.

Прямые альтернативы:

1. **Без лимита** — спам при первом запуске (50+ постов).
2. **Жёсткий лимит в коде** — нет гибкости под конкретный канал.
3. **Лимит по времени** — сложнее реализовать, менее предсказуемо.
4. **max_new_posts_per_run в конфиге** — гибко, просто, предсказуемо.

## Decision

Добавить параметр **max_new_posts_per_run** (по умолчанию 5).

Реализация:

- **Конфиг:** `src/models.py` → `AppConfig.max_new_posts_per_run: int = 5`
- **YAML:** `config/settings.yaml` → `max_new_posts_per_run: 5`
- **Применение:** `src/main.py::check_sources()`
  - `max_to_send = app_config.max_new_posts_per_run`
  - `entries_to_send = new_entries[:max_to_send]`
  - `skipped_count = total_new - len(entries_to_send)` — логируется

## Consequences

**Положительные:**

- Защита от спама при первом запуске.
- Контроль скорости публикации (не более 5 постов за 5 минут).
- Возможность тонкой настройки под конкретный канал.
- В сочетании с cutoff_date (ADR 0007) даёт предсказуемое поведение.

**Отрицательные:**

- Посты, не влезшие в лимит, игнорируются (принято как feature).
- Если лимит слишком маленький, а поток постов большой — можно «не успевать» за публикациями. На Этапе 2 нужно будет пересмотреть.

**Что теперь нельзя / не нужно:**

- Не нужно хардкодить лимит в коде — только в YAML.
- Не нужно реализовывать очередь отложенной отправки на Этапе 1 — лишнее усложнение.

# ADR 0011: Отключение превью ссылок по умолчанию

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0008 (maxapi), ADR 0012 (единый источник моделей)

## Context

При отправке ссылок в MAX автоматически генерируется превью (картинка + описание). Для новостного канала это создаёт визуальный шум и дублирование контента.

Прямые альтернативы:

1. **Оставить превью включённым** — дублирование контента, визуальный шум.
2. **Настраивать per-channel** — избыточно на Этапе 1.
3. **Отключить по умолчанию** — чисто, просто, соответствует контенту.

У нас уже есть своя картинка (featured image) и описание (excerpt). Превью ссылки дублирует эту информацию.

## Decision

Установить **disable_link_preview: true** по умолчанию.

Реализация:

- **Модуль:** `src/models.py` → `MaxChannelConfig.disable_link_preview: bool = True`
- **YAML:** `config/settings.yaml` → `disable_link_preview: true`
- **Применение:** `src/exporter.py::MaxExporter.export()` → `disable_link_preview=self.config.disable_link_preview`

## Consequences

**Положительные:**

- Чистый вид сообщений.
- Нет дублирования контента (у нас уже есть featured image и описание).
- Соответствует ADR 0008 — maxapi поддерживает флаг из коробки.

**Отрицательные:**

- Ссылка не разворачивается в превью (но это и не нужно).
- Если контент поста не содержит картинки и описания — сообщение будет «сухим». На Этапе 2 можно будет добавить per-channel настройку.

**Что теперь нельзя / не нужно:**

- Не нужно вручную чистить превью из текста — флаг отключает его на стороне MAX.
===== 0012-adr-single-source-pydantic-models.md =====
# ADR 0012: Единый источник Pydantic-моделей — src/models.py

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0006 (pydantic-settings), ADR 0011 (disable_link_preview)

## Context

В проекте было дублирование Pydantic-моделей:

- `src/config.py` определял `FieldMapping`, `MaxChannelConfig`, `ExportConfig`, `SourceConfig`, `AppConfig`, `Secrets`.
- `src/models.py` определял **те же самые** классы.
- `src/exporter.py` импортировал `from .models import MaxChannelConfig`.
- `src/main.py` импортировал `from .config import load_settings`, который возвращал `AppConfig` из `config.py`.

Проблема: в рантайме сосуществовали два набора классов. Это приводило к рассинхрону дефолтов (ADR 0011: `disable_link_preview` — `True` в `config.py`, `False` в `models.py`). Работало случайно: `MaxExporter` получал конфиг из `config.py`, а `parser.py` — только тип из `models.py`.

Риск: при рефакторинге (перестановке импортов) поведение изменилось бы незаметно. Type-checker не поймал бы — классы структурно идентичны.

## Decision

Оставить **`src/models.py`** единственным источником Pydantic-моделей.  
`src/config.py` — только загрузка YAML + `.env` и возврат `AppConfig` из `models.py`.

Реализация:

- **`src/models.py`** — единственный источник:
  - `FieldMapping`
  - `MaxChannelConfig` (с `disable_link_preview: bool = True`)
  - `ExportConfig`
  - `SourceConfig`
  - `AppConfig`
  - `Secrets`
- **`src/config.py`** — только:
  ```python
  from pathlib import Path
  import yaml
  from .models import AppConfig, Secrets

  def load_settings() -> tuple[AppConfig, Secrets]:
      yaml_path = Path("config/settings.yaml")
      if not yaml_path.exists():
          raise FileNotFoundError("Не найден config/settings.yaml")
      with open(yaml_path, encoding="utf-8") as f:
          yaml_data = yaml.safe_load(f) or {}
      return AppConfig(**yaml_data), Secrets()
    ```
- src/exporter.py — без изменений (импортирует из models.py).
- src/parser.py — без изменений (импортирует из models.py).
- src/main.py — без изменений (импортирует load_settings из config.py).

##   Consequences

**Положительные:**

- Один источник истины — models.py.
- Дефолты не расходятся.
- Type-checker ловит несоответствия.
- Проще рефакторить — не нужно искать, какой из двух классов используется.

**Отрицательные:**

- config.py стал тоньше — только загрузка. Кому-то может показаться, что «конфиг» теперь в двух местах, но на самом деле — в одном (models.py + settings.yaml).
- Потребовалась аккуратная миграция дефолтов (взяли верные из config.py, а не из models.py).

**Что теперь нельзя / не нужно:**

- Не нужно определять Pydantic-модели в config.py — только в models.py.
- Не нужно импортировать модели из config.py — только из models.py.
- Не нужно держать два набора дефолтов — только один, в models.py.

# ADR 0013: Синхронный парсер как временное исключение

- **Status:** Accepted
- **Date:** 2026-09-10
- **Related:** ADR 0004 (WP REST API), ADR 0005 (asyncio), ADR 0016 (Этап 2)

## Context

Вся архитектура построена на asyncio (ADR 0005): асинхронный `main.py`, `exporter.py`, `state.py`. Однако `WordPressParser` на Этапе 1 использует синхронный `httpx.Client` и блокирует event loop на время HTTP-запроса к WP API (1–5 секунд).

Причины:
1. На Этапе 1 один источник и один канал — блокировка не критична.
2. Переход на `AsyncClient` требует изменения сигнатуры `fetch_posts()` и всех вызовов.
3. На Этапе 1 важнее стабильность, чем асинхронность парсера.

## Decision

Оставить `WordPressParser` синхронным на Этапе 1. Использовать `httpx.Client` вместо `httpx.AsyncClient`. Метод `fetch_posts()` — обычный `def`, не `async def`.

**На Этапе 2 (задача S2-11) парсер будет переведён на `AsyncClient`.** Это станет обязательным при добавлении второго канала (ВК, Этап 3) и нескольких источников.

## Consequences

**Положительные:**
- Меньше кода на Этапе 1.
- Стабильность: синхронный код проще отлаживать.

**Отрицательные:**
- Блокировка event loop на 1–5 секунд при запросе к WP API.
- При добавлении второго канала (Этап 3) блокировка усилится.

**Что теперь нельзя:**
- Нельзя добавлять новые HTTP-запросы в парсер без перевода его в async.
- Нельзя использовать парсер в FastAPI (Этап 4) без перевода в async.

**Следующий шаг:**
- S2-11: Перевести парсер в async (Этап 2).

# ADR 0016: Этап 2 — Фильтрация по рубрикам и тегам + unit-тесты

- **Status:** In Progress
- **Date:** 2026-09-15
- **Updated:** 2026-09-16
- **Related:** ADR 0004 (WP REST API), ADR 0005 (asyncio), ADR 0009 (JSON state), ADR 0012 (модели), ADR 0013 (синхронный парсер), ADR 0015 (план миграции), ADR 0020 (структура модулей)

## Context

Этап 1 закрыл базовый сценарий: получить посты из WP REST API, отфильтровать по cutoff_date, отправить в MAX, сохранить state. Фильтрация по категориям/тегам частично реализована в коде (`_should_exclude`, `?categories=`), но:

- не покрыта тестами;
- не проверена на реальных данных;
- не зафиксирована как «готовое» решение.

**Критические архитектурные проблемы Этапа 1:**
1. **Нарушение SRP**: `_clean_description()` дублировался в парсере и экспортере.
2. **`.get()` маскировал ошибки**: если парсер не извлёк данные, экспортер молча подставлял пустую строку.
3. **Парсер синхронный**: блокирует event loop на время HTTP-запроса к WP API.

Перед добавлением тестов (S2-01) и второго канала (Этап 3) нужно исправить эти проблемы.

## Decision

1. Сначала исправить архитектурные проблемы Этапа 1 (S2-09, S2-10).
2. Затем перевести парсер в async (S2-11) — до написания тестов, чтобы не переписывать их.
3. Затем настроить pytest (S2-01).
4. Затем покрыть тестами фильтрацию (S2-02…S2-08).
5. Добавить батчинг `_save()` в StateManager (S2-12) — оптимизация записи состояния.

# ADR 0017: Этап 3 — Интеграция с ВКонтакте

- **Status:** Planned
- **Date:** 2026-09-15
- **Related:** ADR 0005 (asyncio), ADR 0008 (maxapi), ADR 0009 (state), ADR 0011 (disable_link_preview), ADR 0012 (модели), ADR 0016 (Этап 2), ADR 0022 (VK API)

## Context

Этап 1 дал один канал — MAX. Этап 3 добавляет второй канал — ВКонтакте. Это первая проверка архитектуры на мультиканальность: экспортёр, state, конфиг должны выдержать второго потребителя.

ВК API существенно отличается от MAX:
- Авторизация через `access_token` + `owner_id` (ID группы со знаком минус).
- Публикация на стену группы — `wall.post`.
- Загрузка изображений — двухшаговая: `photos.getWallUploadServer` → `photos.saveWallPhoto`.
- Лимит текста — 5000 символов.
- Rate limit — 3 запроса в секунду на `wall.post`.

## Decision

Добавить `VkExporter` с интерфейсом, совместимым с `MaxExporter`. Расширить `StateManager` для хранения ID по каналам. Не менять архитектуру асинхронности (ADR 0005).

**Мультиканальность — последовательный цикл, не `asyncio.gather`.** На Этапе 3 каналов два. `asyncio.gather` даст выигрыш только при 5+ каналах, а пока усложнит обработку ошибок и порядок логирования. Зафиксировано: переход на `gather` — триггер Этапа 5 (S5-04), не раньше.

**Фильтры per-channel — не в Этапе 3.** В наброске была идея `vk_include_category_ids` / `vk_exclude_category_ids` в `SourceConfig`. Это усложняет конфиг и модель данных. Отложено до Этапа 5 (S5-02), когда фильтры переедут в БД и станут per-channel естественным образом.

**Структура exporter.py → exporters/.** При добавлении второго канала модуль `src/exporter.py` превращается в пакет `src/exporters/` с файлами `max_exporter.py` и `vk_exporter.py`. Это зафиксировано в ADR 0020 (раздел "Эволюция структуры").

# ADR 0018: Этап 4 — Веб-интерфейс, Docker, PostgreSQL

- **Status:** Planned
- **Date:** 2026-09-15
- **Related:** ADR 0005 (asyncio), ADR 0009 (JSON state), ADR 0017 (мультиканальность), ADR 0019 (Этап 5)

## Context

Этапы 1–3 дают рабочий мультиканальный репостер, но управление — через YAML и `.env`. Этап 4 превращает его в сервис с веб-управлением, БД и Docker-развёртыванием.

Ключевые изменения:
- `while True` → APScheduler внутри FastAPI lifespan.
- `state.json` → PostgreSQL (с возможностью SQLite для локальной разработки).
- Локальный запуск → Docker + Angie.

## Decision

Перейти на FastAPI + APScheduler. Мигрировать state на PostgreSQL (SQLAlchemy + Alembic). Развернуть в Docker на `docker_host` за Angie.

**SQLite для локальной разработки** — оставляем. `DATABASE_URL` позволяет переключаться без изменения кода. SQLite — не для прода, только для локального запуска и тестов.

**Angie** — часть Этапа 4, не «Этап 4+». Развёртывание на `docker_host` без reverse proxy не имеет смысла.

# ADR 0019: Этап 5 — Продвинутый UI и мультиканальность

- **Status:** Planned
- **Date:** 2026-09-15
- **Related:** ADR 0017 (Этап 3), ADR 0018 (Этап 4)

## Context

Этап 4 даёт базовый веб-интерфейс и БД. Этап 5 — динамическая конфигурация без перезапуска, продвинутая фильтрация, мониторинг.

Здесь же закрываются два отложенных вопроса:
1. **Фильтры per-channel.** В Этапе 3 была идея `vk_include_category_ids`. Отложено до Этапа 5, когда фильтры переедут в БД.
2. **`asyncio.gather` для каналов.** На Этапе 3 — последовательный цикл. Триггер перехода на `gather` — 5+ каналов.

## Decision

Перенести все настройки из YAML в БД. Фильтры — per-channel. Добавить мониторинг и алерты. Готовить систему к продакшену.

**Celery + Redis** — только если APScheduler не справится (триггер: задачи не успевают за интервал, нужна распределённая блокировка). До этого — APScheduler.

**`asyncio.gather`** — триггер 5+ каналов.

===== 0020-modules-structure-and-responsibilities.md =====
# ADR 0020: Структура модулей и зоны ответственности

- **Status:** Accepted
- **Date:** 2026-09-16
- **Related:** ADR 0004 (WP REST API), ADR 0005 (asyncio), ADR 0009 (JSON state), ADR 0012 (модели), ADR 0016 (Этап 2, S2-09), ADR 0017 (Этап 3)

## Context

На Этапе 1 возникло дублирование кода: метод `_clean_description()` присутствовал и в парсере (`WordPressParser._clean_text()`), и в экспортере (`MaxExporter._clean_description()`). Это привело к тому, что:

1. **Парсер** очищал текст от HTML, `[...]`, `…`, нормализовал пробелы.
2. **Экспортер** снова очищал текст (дублирование логики).
3. **Использование `.get()` в экспортере** маскировало ошибки: если парсер не извлёк данные, экспортер молча подставлял пустую строку.

Причина: **не были зафиксированы границы ответственности модулей**. Каждый разработчик (или LLM) добавлял очистку туда, где было удобно, без понимания, кто за что отвечает.

## Decision

Зафиксировать структуру модулей и зоны ответственности. Каждый модуль отвечает **только за свою задачу**.

### Структура проекта (Этап 1–2)

```
src/
├── main.py          # Точка входа, оркестрация циклов
── parser.py        # Извлечение и нормализация данных из WP API
├── exporter.py      # Форматирование и отправка в каналы (MAX)
├── state.py         # Хранение состояния (processed posts, cutoff_date)
├── models.py        # Pydantic-модели (конфигурация, секреты)
└── config.py        # Загрузка конфигов из YAML и .env
```

### Эволюция структуры при мультиканальности (Этап 3+)

При добавлении второго канала (ВК) модуль `src/exporter.py` превращается в пакет `src/exporters/`:

```
src/
├── main.py
├── parser.py
├── exporters/
│   ├── __init__.py
│   ├── max_exporter.py
│   └── vk_exporter.py
├── state.py
├── models.py
└── config.py
```

**Правило:** Каждый канал — отдельный файл в пакете `exporters/`. Интерфейс единый: `async def export(entry, image_url) -> str | None`.

### Зоны ответственности

#### 1. `src/parser.py` — Извлечение и нормализация данных

**Отвечает за:**
- HTTP-запросы к WP REST API (`/wp-json/wp/v2/posts`)
- Парсинг JSON-ответа
- Извлечение полей: `title`, `content`, `link`, `published`, `_image_url`
- **Очистку текста**: удаление HTML-тегов, декодирование сущностей (`&hellip;`, `&#8230;`), удаление артефактов `[...]` и `…`, нормализация пробелов, добавление точки в конце
- Фильтрацию по категориям/тегам (`_should_exclude()`)
- Пагинацию и `cutoff_date`

**Возвращает:**
```python
{
    "title": "Заголовок поста",
    "content": "Очищенный текст без HTML, с точкой в конце",
    "link": "https://example.com/post",
    "published": "2026-09-15T10:30:00",
    "_image_url": "https://example.com/image.jpg"  # или None
}
```

**Не отвечает за:**
- Форматирование по шаблону
- Отправку в каналы
- Хранение состояния

#### 2. `src/exporter.py` (Этап 1–2) / `src/exporters/*.py` (Этап 3+) — Форматирование и отправка

**Отвечает за:**
- Получение готовых данных от парсера
- Подстановку в шаблон (`template.format(...)`)
- Скачивание изображений по URL
- Загрузку изображений в канал (MAX, VK)
- Отправку сообщения через API канала
- Возврат `message_id` при успехе

**Не отвечает за:**
- Очистку текста от HTML
- Декодирование сущностей
- Удаление `[...]` и `…`
- Добавление точки в конец

**Правило:** Экспортер получает **полностью подготовленные данные** от парсера. Никакой логики очистки в экспортере быть не должно.

#### 3. `src/state.py` — Хранение состояния

**Отвечает за:**
- Загрузку/сохранение `data/state.json`
- Проверку, был ли пост уже обработан (`is_processed()`)
- Запись о новом отправленном посте (`mark_processed()`)
- Обновление `cutoff_date` (`update_cutoff_date()`)

**Не отвечает за:**
- HTTP-запросы
- Форматирование
- Отправку

#### 4. `src/models.py` — Pydantic-модели

**Отвечает за:**
- Определение структуры конфигурации (`AppConfig`, `SourceConfig`, `MaxChannelConfig`)
- Определение структуры секретов (`Secrets`)
- Валидацию типов и значений

**Не отвечает за:**
- Загрузку конфигов (это делает `config.py`)
- Бизнес-логику

#### 5. `src/config.py` — Загрузка конфигов

**Отвечает за:**
- Чтение `config/settings.yaml`
- Чтение `.env` через `pydantic-settings`
- Возврат объектов `AppConfig` и `Secrets`

**Не отвечает за:**
- Бизнес-логику
- HTTP-запросы

#### 6. `src/main.py` — Оркестрация

**Отвечает за:**
- Загрузку конфигов
- Инициализацию парсера, экспортера, state manager
- Цикл проверки источников
- Обработку сигналов остановки (`Ctrl+C`)
- Закрытие сетевых сессий

**Не отвечает за:**
- Детали парсинга
- Детали отправки
- Детали хранения состояния

### Правила взаимодействия

1. **Парсер → Экспортер:** Парсер возвращает полностью подготовленные данные. Экспортер только форматирует и отправляет.
2. **Экспортер → State:** Экспортер возвращает `message_id`. `main.py` передаёт его в `state.mark_processed()`.
3. **State → Парсер:** `main.py` передаёт `cutoff_date` из state в парсер.
4. **Models → Все:** Модели используются всеми модулями для типизации.

### Последствия для S2-09

Задача **S2-09** (разделение ответственности парсера и экспортера) является **прямым следствием** этого ADR:

1. Удалить `_clean_description()` из `MaxExporter`.
2. Убедиться, что `WordPressParser._format_post()` возвращает полностью очищенный `content`.
3. В `MaxExporter.format_post()` использовать прямой доступ `entry["title"]` вместо `entry.get("title", "")` (S2-10).

## Consequences

**Положительные:**
- Чёткие границы ответственности.
- Нет дублирования кода.
- Легко добавлять новые каналы (только новый exporter, парсер не меняется).
- Легко тестировать (каждый модуль изолирован).

**Отрицательные:**
- Требуется дисциплина: нельзя добавлять логику очистки в экспортер.
- При изменении формата данных нужно обновлять и парсер, и экспортер.

**Что теперь нельзя:**
- Нельзя дублировать `_clean_description()` в парсере и экспортере.
- Нельзя использовать `.get()` в экспортере для маскировки ошибок парсера.
- Нельзя добавлять HTTP-логику в экспортер (только в парсер).
- Нельзя добавлять бизнес-логику в `models.py` или `config.py`.

**Следующий шаг:**
- S2-09: Рефакторинг — разделение ответственности парсера и экспортера.
- S2-10: Заменить `.get()` на прямой доступ с валидацией.

# ADR 0001: Дамп репозитория в один файл для LLM

- **Status:** Proposed
- **Date:** 2026-09-15

## Context

При работе с LLM (ChatGPT, Claude, локальные модели) над проектом
возникает задача передать модели контекст: структуру и содержимое
кода. Ручное копирование файлов в чат — медленно, ведёт к пропускам
и не воспроизводится.

Прямые альтернативы:

1. **Готовые инструменты** (Repomix, code2prompt, Gitingest) —
   зрелые, но тянут зависимости (Node.js, Rust), избыточны для
   небольших проектов, и часть из них отправляет код на свои серверы.
2. **Ручной сбор** — не масштабируется, легко забыть файл.
3. **MCP-серверы** — требуют настройки клиента, привязывают к
   конкретному инструменту (Claude Desktop, Cursor).

Контекстное окно LLM также накладывает ограничение: дамп должен
быть предсказуем по объёму, чтобы не улететь в «жёлтую зону»
деградации качества (>50–80k токенов).

Проект современный, все файлы в UTF-8. Поддержка legacy-кодировок
(Windows-1251, UTF-16) — лишняя сложность для инструмента,
рассчитанного на небольшие актуальные репозитории.

Отдельный риск: случайно закоммиченный `.env` или `credentials.json`
попадёт в дамп и уйдёт в облачную LLM. Это не гипотетический сценарий:
коммит `.env` — одна из самых частых ошибок в небольших проектах,
где нет pre-commit-хуков и review-процесса. Утечка необратима:
даже если потом удалить файл из репозитория и перегенерировать дамп,
содержимое остаётся в истории чата с моделью.

## Decision

Написан собственный скрипт `project_dump.py`, который:

- запускается из корня репозитория;
- использует `git ls-files` для получения списка отслеживаемых
  файлов — так `.gitignore`, вложенные `.gitignore` и глобальный
  `~/.gitignore` работают автоматически, без парсинга своими руками;
- пропускает бинарные файлы (эвристика по NUL-байту в первых 8 KB;
  ложные срабатывания на UTF-16 — см. Consequences);
- пропускает lock-файлы и сгенерированный код через `EXCLUDE_PATTERNS`;
- пропускает Markdown-файлы (`*.md`) — документация полезна человеку,
  но в дампе кода для LLM она только занимает токены. При
  необходимости конкретный `.md` можно вернуть в дамп через
  добавление в `ALLOW_PATTERNS`;
- нормализует переносы строк к `\n` при чтении: файлы с CRLF
  (Windows-переносы) в дампе выглядят единообразно, без лишних
  `\r`, которые редакторы отображают как пустые строки;
- исключает из дампа потенциальные секреты: `.env`, ключи и
  сертификаты (`*.key`, `*.pem`, `*.p12`), `credentials.*`,
  `secrets.*`, SSH-ключи, конфиги облачных сервисов;
- эвристика «похоже на секрет» проверяет имя файла по подстрокам
  (`secret`, `password`, `credential`, `token`, `apikey`, `api_key`,
  `private`). Hint `auth` исключён из списка: он даёт массовые
  ложные срабатывания на документации (`AUTHORS`, `authentication.md`,
  `authorization.md`). Файлы вида `auth.json` с токенами эвристикой
  не ловятся — это осознанный компромисс;
- сравнивает имена файлов с паттернами регистронезависимо и
  кроссплатформенно: `*.KEY`, `*.key`, `Private.Key` отсеиваются
  одинаково на Windows и Linux. Реализовано через `fnmatchcase`
  с ручной нормализацией регистра;
- сохраняет в дампе шаблоны `.env` без реальных секретов
  (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`):
  они полезны, чтобы LLM видел ожидаемые переменные окружения.
  Реализовано через allow-list, который проверяется после
  пользовательских `-x`, но до встроенных `EXCLUDE_PATTERNS`;
- пишет результат в `project_dump.txt` с оглавлением в начале
  и заголовками `===== path =====` перед каждым файлом;
- печатает предварительную оценку объёма в байтах и токенах до
  записи, предупреждает при превышении порога;
- поддерживает флаги:
  - `-o` — имя выходного файла;
  - `-x` / `--exclude` — дополнительный glob-паттерн исключения;
  - `--no-toc` — отключить оглавление;
  - `--max-bytes` — прервать при превышении лимита;
  - `--no-default-excludes` — не применять встроенные исключения
    (для отладки или если фильтрация не нужна);
  - `--force` — продолжить, несмотря на найденные подозрительные файлы;
- использует коды возврата: 0 — успех, 1 — ошибка git, 2 — превышен
  `--max-bytes`, 3 — нечего дампить, 4 — найдены файлы, похожие
  на секреты (нужен `--force`).

Скрипт остаётся одним файлом без внешних зависимостей (только
стандартная библиотека). Это осознанный выбор в пользу простоты
для небольших проектов.

## Consequences

**Положительные:**

- Воспроизводимость: один и тот же дамп получается на любой машине
  с тем же набором закоммиченных файлов.
- Кроссплатформенная воспроизводимость: одинаковые правила
  сравнения имён файлов на Windows и Linux, дампы совпадают
  по составу независимо от ОС.
- Дамп в LF независимо от исходных переносов: результат
  воспроизводим между Windows и Linux, редакторы не показывают
  «фантомных» пустых строк.
- Пустой результат (все файлы отфильтрованы) не создаёт файл
  и завершается с кодом 3 — защита от случайной передачи пустого
  дампа в LLM.
- Нулевые зависимости: работает на голом Python 3.9+.
  Более старые версии (включая 3.5) не поддерживаются из-за
  f-strings, `subprocess.run(capture_output=...)` и PEP 585-аннотаций
  (`list[str]`, `dict[str, int]`).
- Прозрачность: скрипт читается за 5 минут, все настройки в шапке.
- Контроль объёма: оценка токенов до записи, `--max-bytes`,
  `-x` / `--exclude`.
- Защита от случайной утечки секретов: подозрительные файлы
  блокируют запись дампа до явного подтверждения через `--force`.
- Шаблоны `.env.example` остаются в дампе, давая LLM контекст
  о переменных окружения проекта.

**Отрицательные:**

- Не масштабируется на очень большие проекты: полный дамп может
  не влезть в контекст, придётся дампить поддеревья вручную.
- Оценка токенов грубая (`bytes / 4`), погрешность ±20%.
- `git ls-files --cached` не видит неотслеживаемые файлы, что
  обычно правильно, но требует `git add` для новых файлов.
- Нет автоматической интеграции с LLM-клиентами (в отличие от
  MCP-серверов), каждый раз нужно копировать результат в чат.
- Не поддерживаются файлы в кодировках, отличных от UTF-8:
  Windows-1251 и подобные не отсеиваются эвристикой бинарности
  (NUL-байта в них нет) и попадают в дамп с заглушками `�`.
  Скрипт предупреждает об этом в stderr с указанием файла и
  позиции ошибки, но не блокирует запись.
- Эвристика бинарности (поиск NUL-байта) ложно срабатывает на
  UTF-16: такие файлы будут пропущены как бинарные. Для
  UTF-8-проектов это не проблема, для смешанных — потребуется
  доработка.
- Защита от секретов работает только по имени файла. Файлы с
  нейтральным именем (`config.yaml`) или с `auth` в имени
  (`auth.json`), содержащие ключи или пароли, в дамп попадут.
  Проверка содержимого на паттерны (`AKIA...`,
  `-----BEGIN PRIVATE KEY-----` и т.п.) в текущем решении
  не реализована.
- Эвристика «похоже на секрет» может давать ложные срабатывания
  на файлах с `token`, `password`, `credential`, `private` в имени
  (например, `tokenizer.md`, `password_policy.yaml`). Лечится
  флагом `--force` или добавлением в `-x`.
- Allow-list шаблонов `.env` может устареть: если в проекте
  появится новый формат шаблона (например, `.env.local.example`),
  его нужно добавить в `ALLOW_PATTERNS`. Пользователь может
  явно исключить шаблон через `-x`, если он не нужен.

**Что теперь нельзя / не нужно:**

- Не нужно парсить `.gitignore` самостоятельно — git делает это
  лучше.
- Вывод `project_dump.txt` прописан в `.gitignore`, поэтому git
  его не отслеживает. Это даёт две вещи: файл не попадёт в коммит
  случайно, и `git ls-files` его не вернёт, то есть в сам дамп он
  тоже не попадёт — без дополнительных исключений в скрипте.

# ADR 0002: Менеджер пакетов — uv

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0003 (ruff), ADR 0012 (единый источник моделей)

## Context

Нужен современный менеджер пакетов для Python-проекта: lock-файлы, группы зависимостей (dev/prod), быстрая установка, нативная поддержка Windows, лёгкая интеграция с Docker.

Прямые альтернативы:

1. **pip + requirements.txt** — стандарт де-факто, но нет lock-файлов, нет групп зависимостей, медленная установка.
2. **Poetry** — зрелый, но медленнее, свой DSL для конфигов (`[tool.poetry]`), тяжелее для Docker-образов.
3. **PDM** — менее зрелый, меньше комьюнити.

## Decision

Использовать **uv** от Astral.

Реализация:

- **Файл:** `pyproject.toml`
- **Секции:** `[project].dependencies`, `[dependency-groups].dev`
- **Ключевые поля:**
  - `requires-python = ">=3.12"`
  - Зависимости: `httpx>=0.27.0`, `pydantic>=2.7.0`, `pydantic-settings>=2.2.0`, `pyyaml>=6.0.1`, `maxapi>=1.2.0`
  - Dev-группа: `pytest>=8.2.0`, `pytest-asyncio>=0.23.6`, `respx>=0.21.0`, `ruff>=0.4.0`
- **Lock-файл:** `uv.lock` — в репозитории есть. **Осознанно не включается в дамп TOC** (см. ADR 0001: `EXCLUDE_PATTERNS` пропускает lock-файлы, чтобы не раздувать дамп).

## Consequences

**Положительные:**

- Скорость установки в 10–100 раз выше pip/poetry (написан на Rust).
- Детерминированные сборки через `uv.lock`.
- Группы зависимостей без дополнительного DSL.
- Полная совместимость с pip-экосистемой.
- Нативная поддержка Windows.
- Лёгкие Docker-образы на Этапе 4.

**Отрицательные:**

- Экосистема менее зрелая, чем у poetry (но быстро развивается).
- `uv.lock` не виден в дампе TOC — LLM не сможет увидеть точные зафиксированные версии. При необходимости можно передать `uv.lock` в чат отдельно.

**Что теперь нельзя / не нужно:**

- Не нужно вести `requirements.txt` параллельно — источник истины один, `pyproject.toml`.
- Не нужно парсить `pyproject.toml` вручную для установки — uv делает это сам.
- Не нужно добавлять `uv.lock` в дамп TOC — это осознанное решение (см. ADR 0001).

# ADR 0004: Источник данных — WordPress REST API вместо RSS

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0007 (cutoff_date), ADR 0013 (синхронный парсер)

## Context

Изначально планировался парсинг RSS-ленты WordPress. Но RSS:

- не отдаёт featured images (только `<enclosure>`, если повезёт);
- требует сложного парсинга HTML из `<description>`;
- не поддерживает серверную фильтрацию по категориям и тегам;
- отдаёт XML, который нужно парсить.

WordPress REST API (`/wp-json/wp/v2/posts`) — встроен в ядро WP, отдаёт JSON, поддерживает `_embed`, `categories`, `after`.

Прямые альтернативы:

1. **RSS + парсинг HTML** — нет featured images, сложный парсинг, нет серверной фильтрации.
2. **WP XML-RPC** — устаревший протокол, ограниченный функционал.
3. **Скрейпинг HTML** — хрупко, ломается при изменении вёрстки.
4. **WP REST API** — встроен, JSON, `_embed`, серверная фильтрация.

Риск: не все WP-сайты держат REST API открытым. Но для новостных сайтов это обычно так.

## Decision

Использовать **WordPress REST API** (`/wp-json/wp/v2/posts`).

Реализация:

- **Модуль:** `src/parser.py`
- **Класс:** `WordPressParser`
- **Методы:**
  - `__init__()` — формирует `self.api_url = f"{base_url}{source.api_path}"`
  - `fetch_posts()` — GET `/posts` с параметрами `_embed`, `orderby=date`, `order=desc`, `per_page`, `page`, `after`, `categories`
  - `_extract_image()` — извлекает URL из `_embedded["wp:featuredmedia"][0]["media_details"]["sizes"][featured_image_size]`, с fallback на первый доступный размер
  - `_should_exclude()` — фильтрация по `_embedded["wp:term"]` (категории — `terms[0]`, теги — `terms[1]`)
  - `_format_post()` — преобразует ответ API во внутренний формат `{id, link, title, content, published, _image_url}`
  - `_clean_text()` — очистка HTML и сущностей
- **Конфиг источника:** `src/models.py` → `SourceConfig`
  - `base_url`, `api_path = "/wp-json/wp/v2"`
  - `featured_image_size = "medium"`
  - `max_pages = 3`, `per_page = 20`
  - `include_category_ids`, `exclude_category_ids`, `include_tag_ids`, `exclude_tag_ids`

## Consequences

**Положительные:**

- Featured images с размерами (`thumbnail`, `medium`, `large`) из коробки.
- Серверная фильтрация по категориям — меньше трафика.
- Чистый JSON вместо XML + HTML.
- `_embed` для получения связанных данных одним запросом.
- Пагинация через `?page=N&per_page=20`.

**Отрицательные:**

- Требует доступа к WP REST API. Если сайт отключил REST API — не работает.
- `_should_exclude()` жёстко привязан к порядку `wp:term[0]` / `wp:term[1]`. Если WP вернёт термы в другом порядке — сломается. На Этапе 2 нужно уточнить (см. план правок).
- `_extract_image()` делает fallback на первый доступный размер, если запрошенного нет. Это может привести к неожиданно большому изображению.

**Что теперь нельзя / не нужно:**

- Не нужно парсить RSS и XML.
- Не нужно чистить HTML от `<description>` — API отдаёт `excerpt.rendered` и `content.rendered`, которые чистит `_clean_text()`.

===== 0007-adr-cutoff-date-spam-protection.md =====
# ADR 0007: Защита от спама через cutoff_date

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0010 (лимит постов), ADR 0009 (JSON state)

## Context

При первом запуске API может вернуть 50+ старых постов. Если отправить всё сразу — спам в канале. Если лимитировать отправку, но не сдвигать границу времени — старые посты будут приходить снова и снова.

Прямые альтернативы:

1. **Отправлять всё при первом запуске** — спам.
2. **Хранить все GUID и проверять** — состояние разрастается, логика усложняется.
3. **Лимит без cutoff_date** — старые посты приходят повторно.
4. **cutoff_date с движением вперёд** — простая логика, предсказуемое поведение.

## Decision

Использовать **cutoff_date** (дата отсечки) с движением только вперёд во времени.

Как работает:

1. После первого запуска граница = дата **самого нового** отправленного поста.
2. В следующий раз API возвращает только посты новее (`?after=cutoff_date`).
3. Старые посты игнорируются навсегда.

Реализация:

- **Модуль:** `src/state.py` → `StateManager`
  - Поле `last_processed_date: str | None`
  - `_load()` — читает `last_processed_date` из JSON
  - `_save()` — сохраняет `last_processed_date`
  - `update_cutoff_date(date_str)` — обновляет и сохраняет; докстринг: «Обновляет дату отсечки (самый новый пост, который мы взяли в работу)»
- **Модуль:** `src/parser.py` → `WordPressParser.fetch_posts(cutoff_date)`
  - `if cutoff_date: params["after"] = cutoff_date`
- **Модуль:** `src/main.py` → `check_sources()`
  - `state.last_processed_date` передаётся в `parser.fetch_posts()`
  - `newest_sent_date = entry.get("published")` — берётся первый (самый новый) отправленный пост
  - `state.update_cutoff_date(newest_sent_date)`

## Consequences

**Положительные:**

- Гарантия отсутствия спама устаревшим контентом.
- Предсказуемое поведение при первом запуске.
- Простая логика — движение только вперёд.
- Не нужно хранить все GUID для защиты от повторов — cutoff_date отсекает старые посты на стороне API.

**Отрицательные:**

- Посты, не влезшие в лимит при первом запуске, теряются навсегда (принято как feature).
- Если `published` у поста — не дата, а что-то другое (например, `null`), cutoff_date сломается. Нужно будет уточнить на Этапе 2.

**Что теперь нельзя / не нужно:**

- Не нужно проверять все GUID при каждом запросе — API отдаёт только посты новее cutoff_date.
- Не нужно сдвигать cutoff_date назад — только вперёд.
- Не нужно удалять `last_processed_date` из состояния без явного сброса — иначе вернётся «хвост» старых постов.

# ADR 0008: SDK для MAX — maxapi

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0005 (asyncio), ADR 0011 (disable_link_preview)

## Context

Для отправки сообщений в мессенджер MAX рассматривались прямые HTTP-запросы к API и использование официальной библиотеки maxapi.

Прямые альтернативы:

1. **Прямые HTTP-запросы** — нужно писать клиент вручную, нет типизации, нет обработки ошибок.
2. **Сторонние обёртки** — менее надёжны, чем официальный SDK.
3. **maxapi** — официальная Python-библиотека, Pydantic-модели, загрузка медиа, retries.

## Decision

- **Методы:**
  - `__init__()` — `self.bot = Bot(token=...)` при `config.enabled`
  - `export()` — `await self.bot.upload_media(media)`, `await self.bot.send_message(chat_id, text, attachments, disable_link_preview)`
  - Извлечение ID: `result.message.body.mid` с fallback на `result.id` / `result.message_id`
  - `close()` — `await self.bot.session.close()` или `await self.bot.close()`

## Consequences

**Положительные:**

- Типобезопасность (Pydantic-модели для всех объектов).
- Встроенная поддержка загрузки медиа (`InputMedia`, `InputMediaBuffer`).
- Автоматическая обработка ошибок и retries.
- Поддержка webhook и polling из коробки.
- Активное развитие.

**Отрицательные:**

- Зависимость от третьей стороны (но это официальный SDK).
- Нестандартный путь к ID: `result.message.body.mid` вместо `result.message_id`. Приходится писать fallback.
- `close()` использует внутреннюю `bot.session` — если maxapi изменит API, сломается.

**Что теперь нельзя / не нужно:**

- Не нужно писать HTTP-клиент для MAX вручную.
- Не нужно парсить ответы MAX вручную — maxapi отдаёт Pydantic-модели.

# ADR 0009: JSON state хранение

- **Status:** Accepted
- **Date:** 2026-09-10
- **Related:** ADR 0005 (asyncio), ADR 0018 (Этап 4)

## Context

Необходимо хранить состояние обработанных постов (GUID, message_id, дата отправки) для предотвращения дублирования при перезапуске.

Варианты:
1. **JSON-файл** (`data/state.json`) — просто, прозрачно, но не масштабируется.
2. **SQLite** — локальная БД, но требует миграций.
3. **PostgreSQL** — продакшен, но требует сервера.

На Этапе 1: один источник, один канал, локальный запуск. JSON достаточно.

## Decision

Использовать JSON-файл `data/state.json` для хранения состояния на Этапе 1.

Структура:
```json
{
  "processed_posts": {
    "guid-123": {
      "message_id": "mid.xxx",
      "sent_at": "2026-09-15T10:30:00",
      "channel": "max"
    }
  },
  "last_processed_date": "2026-09-15T10:30:00"
}
```

**На Этапе 4 (задача S4-02) состояние будет мигрировано на PostgreSQL.** Для локальной разработки останется возможность использовать SQLite через `DATABASE_URL`.

## Consequences

**Положительные:**
- Нулевая настройка (просто файл).
- Прозрачность (можно открыть и посмотреть).
- Легко отлаживать.

**Отрицательные:**
- Не подходит для многопользовательской системы (Этап 4+).
- Нет транзакций (риск повреждения при одновременной записи).
- Нет индексов (медленный поиск при большом количестве записей).

**Что теперь нельзя:**
- Нельзя использовать state.json в FastAPI (Этап 4) без миграции на БД.
- Нельзя запускать несколько инстансов репостера с общим state.json.

**Следующий шаг:**
- S4-02: Миграция на PostgreSQL (Этап 4).

# ADR 0010: Лимит постов за один цикл — max_new_posts_per_run

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0007 (cutoff_date)

## Context

Необходимо ограничить количество постов за один цикл проверки, чтобы не перегружать канал и API.

Прямые альтернативы:

1. **Без лимита** — спам при первом запуске (50+ постов).
2. **Жёсткий лимит в коде** — нет гибкости под конкретный канал.
3. **Лимит по времени** — сложнее реализовать, менее предсказуемо.
4. **max_new_posts_per_run в конфиге** — гибко, просто, предсказуемо.

## Decision

Добавить параметр **max_new_posts_per_run** (по умолчанию 5).

Реализация:

- **Конфиг:** `src/models.py` → `AppConfig.max_new_posts_per_run: int = 5`
- **YAML:** `config/settings.yaml` → `max_new_posts_per_run: 5`
- **Применение:** `src/main.py::check_sources()`
  - `max_to_send = app_config.max_new_posts_per_run`
  - `entries_to_send = new_entries[:max_to_send]`
  - `skipped_count = total_new - len(entries_to_send)` — логируется

## Consequences

**Положительные:**

- Защита от спама при первом запуске.
- Контроль скорости публикации (не более 5 постов за 5 минут).
- Возможность тонкой настройки под конкретный канал.
- В сочетании с cutoff_date (ADR 0007) даёт предсказуемое поведение.

**Отрицательные:**

- Посты, не влезшие в лимит, игнорируются (принято как feature).
- Если лимит слишком маленький, а поток постов большой — можно «не успевать» за публикациями. На Этапе 2 нужно будет пересмотреть.

**Что теперь нельзя / не нужно:**

- Не нужно хардкодить лимит в коде — только в YAML.
- Не нужно реализовывать очередь отложенной отправки на Этапе 1 — лишнее усложнение.

# ADR 0011: Отключение превью ссылок по умолчанию

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0008 (maxapi), ADR 0012 (единый источник моделей)

## Context

При отправке ссылок в MAX автоматически генерируется превью (картинка + описание). Для новостного канала это создаёт визуальный шум и дублирование контента.

Прямые альтернативы:

1. **Оставить превью включённым** — дублирование контента, визуальный шум.
2. **Настраивать per-channel** — избыточно на Этапе 1.
3. **Отключить по умолчанию** — чисто, просто, соответствует контенту.

У нас уже есть своя картинка (featured image) и описание (excerpt). Превью ссылки дублирует эту информацию.

## Decision

Установить **disable_link_preview: true** по умолчанию.

Реализация:

- **Модуль:** `src/models.py` → `MaxChannelConfig.disable_link_preview: bool = True`
- **YAML:** `config/settings.yaml` → `disable_link_preview: true`
- **Применение:** `src/exporter.py::MaxExporter.export()` → `disable_link_preview=self.config.disable_link_preview`

## Consequences

**Положительные:**

- Чистый вид сообщений.
- Нет дублирования контента (у нас уже есть featured image и описание).
- Соответствует ADR 0008 — maxapi поддерживает флаг из коробки.

**Отрицательные:**

- Ссылка не разворачивается в превью (но это и не нужно).
- Если контент поста не содержит картинки и описания — сообщение будет «сухим». На Этапе 2 можно будет добавить per-channel настройку.

**Что теперь нельзя / не нужно:**

- Не нужно вручную чистить превью из текста — флаг отключает его на стороне MAX.
===== 0012-adr-single-source-pydantic-models.md =====
# ADR 0012: Единый источник Pydantic-моделей — src/models.py

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0006 (pydantic-settings), ADR 0011 (disable_link_preview)

## Context

В проекте было дублирование Pydantic-моделей:

- `src/config.py` определял `FieldMapping`, `MaxChannelConfig`, `ExportConfig`, `SourceConfig`, `AppConfig`, `Secrets`.
- `src/models.py` определял **те же самые** классы.
- `src/exporter.py` импортировал `from .models import MaxChannelConfig`.
- `src/main.py` импортировал `from .config import load_settings`, который возвращал `AppConfig` из `config.py`.

Проблема: в рантайме сосуществовали два набора классов. Это приводило к рассинхрону дефолтов (ADR 0011: `disable_link_preview` — `True` в `config.py`, `False` в `models.py`). Работало случайно: `MaxExporter` получал конфиг из `config.py`, а `parser.py` — только тип из `models.py`.

Риск: при рефакторинге (перестановке импортов) поведение изменилось бы незаметно. Type-checker не поймал бы — классы структурно идентичны.

## Decision

Оставить **`src/models.py`** единственным источником Pydantic-моделей.  
`src/config.py` — только загрузка YAML + `.env` и возврат `AppConfig` из `models.py`.

Реализация:

- **`src/models.py`** — единственный источник:
  - `FieldMapping`
  - `MaxChannelConfig` (с `disable_link_preview: bool = True`)
  - `ExportConfig`
  - `SourceConfig`
  - `AppConfig`
  - `Secrets`
- **`src/config.py`** — только:
  ```python
  from pathlib import Path
  import yaml
  from .models import AppConfig, Secrets

  def load_settings() -> tuple[AppConfig, Secrets]:
      yaml_path = Path("config/settings.yaml")
      if not yaml_path.exists():
          raise FileNotFoundError("Не найден config/settings.yaml")
      with open(yaml_path, encoding="utf-8") as f:
          yaml_data = yaml.safe_load(f) or {}
      return AppConfig(**yaml_data), Secrets()
    ```
- src/exporter.py — без изменений (импортирует из models.py).
- src/parser.py — без изменений (импортирует из models.py).
- src/main.py — без изменений (импортирует load_settings из config.py).

##   Consequences

**Положительные:**

- Один источник истины — models.py.
- Дефолты не расходятся.
- Type-checker ловит несоответствия.
- Проще рефакторить — не нужно искать, какой из двух классов используется.

**Отрицательные:**

- config.py стал тоньше — только загрузка. Кому-то может показаться, что «конфиг» теперь в двух местах, но на самом деле — в одном (models.py + settings.yaml).
- Потребовалась аккуратная миграция дефолтов (взяли верные из config.py, а не из models.py).

**Что теперь нельзя / не нужно:**

- Не нужно определять Pydantic-модели в config.py — только в models.py.
- Не нужно импортировать модели из config.py — только из models.py.
- Не нужно держать два набора дефолтов — только один, в models.py.

# ADR 0013: Синхронный парсер как временное исключение

- **Status:** Accepted
- **Date:** 2026-09-10
- **Related:** ADR 0004 (WP REST API), ADR 0005 (asyncio), ADR 0016 (Этап 2)

## Context

Вся архитектура построена на asyncio (ADR 0005): асинхронный `main.py`, `exporter.py`, `state.py`. Однако `WordPressParser` на Этапе 1 использует синхронный `httpx.Client` и блокирует event loop на время HTTP-запроса к WP API (1–5 секунд).

Причины:
1. На Этапе 1 один источник и один канал — блокировка не критична.
2. Переход на `AsyncClient` требует изменения сигнатуры `fetch_posts()` и всех вызовов.
3. На Этапе 1 важнее стабильность, чем асинхронность парсера.

## Decision

Оставить `WordPressParser` синхронным на Этапе 1. Использовать `httpx.Client` вместо `httpx.AsyncClient`. Метод `fetch_posts()` — обычный `def`, не `async def`.

**На Этапе 2 (задача S2-11) парсер будет переведён на `AsyncClient`.** Это станет обязательным при добавлении второго канала (ВК, Этап 3) и нескольких источников.

## Consequences

**Положительные:**
- Меньше кода на Этапе 1.
- Стабильность: синхронный код проще отлаживать.

**Отрицательные:**
- Блокировка event loop на 1–5 секунд при запросе к WP API.
- При добавлении второго канала (Этап 3) блокировка усилится.

**Что теперь нельзя:**
- Нельзя добавлять новые HTTP-запросы в парсер без перевода его в async.
- Нельзя использовать парсер в FastAPI (Этап 4) без перевода в async.

**Следующий шаг:**
- S2-11: Перевести парсер в async (Этап 2).

===== 0020-modules-structure-and-responsibilities.md =====
# ADR 0020: Структура модулей и зоны ответственности

- **Status:** Accepted
- **Date:** 2026-09-16
- **Related:** ADR 0004 (WP REST API), ADR 0005 (asyncio), ADR 0009 (JSON state), ADR 0012 (модели), ADR 0016 (Этап 2, S2-09)

## Context

На Этапе 1 возникло дублирование кода: метод `_clean_description()` присутствовал и в парсере (`WordPressParser._clean_text()`), и в экспортере (`MaxExporter._clean_description()`). Это привело к тому, что:

1. **Парсер** очищал текст от HTML, `[...]`, `…`, нормализовал пробелы.
2. **Экспортер** снова очищал текст (дублирование логики).
3. **Использование `.get()` в экспортере** маскировало ошибки: если парсер не извлёк данные, экспортер молча подставлял пустую строку.

Причина: **не были зафиксированы границы ответственности модулей**. Каждый разработчик (или LLM) добавлял очистку туда, где было удобно, без понимания, кто за что отвечает.

## Decision

Зафиксировать структуру модулей и зоны ответственности. Каждый модуль отвечает **только за свою задачу**.

### Структура проекта

```
src/
├── main.py          # Точка входа, оркестрация циклов
├── parser.py        # Извлечение и нормализация данных из WP API
├── exporter.py      # Форматирование и отправка в каналы (MAX, VK)
├── state.py         # Хранение состояния (processed posts, cutoff_date)
├── models.py        # Pydantic-модели (конфигурация, секреты)
└── config.py        # Загрузка конфигов из YAML и .env
```

### Зоны ответственности

#### 1. `src/parser.py` — Извлечение и нормализация данных

**Отвечает за:**
- HTTP-запросы к WP REST API (`/wp-json/wp/v2/posts`)
- Парсинг JSON-ответа
- Извлечение полей: `title`, `content`, `link`, `published`, `_image_url`
- **Очистку текста**: удаление HTML-тегов, декодирование сущностей (`&hellip;`, `&#8230;`), удаление артефактов `[...]` и `…`, нормализация пробелов, добавление точки в конце
- Фильтрацию по категориям/тегам (`_should_exclude()`)
- Пагинацию и `cutoff_date`

**Возвращает:**
```python
{
    "title": "Заголовок поста",
    "content": "Очищенный текст без HTML, с точкой в конце",
    "link": "https://example.com/post",
    "published": "2026-09-15T10:30:00",
    "_image_url": "https://example.com/image.jpg"  # или None
}
```

**Не отвечает за:**
- Форматирование по шаблону
- Отправку в каналы
- Хранение состояния

#### 2. `src/exporter.py` — Форматирование и отправка

**Отвечает за:**
- Получение готовых данных от парсера
- Подстановку в шаблон (`template.format(...)`)
- Скачивание изображений по URL
- Загрузку изображений в канал (MAX, VK)
- Отправку сообщения через API канала
- Возврат `message_id` при успехе

**Не отвечает за:**
- Очистку текста от HTML
- Декодирование сущностей
- Удаление `[...]` и `…`
- Добавление точки в конец

**Правило:** Экспортер получает **полностью подготовленные данные** от парсера. Никакой логики очистки в экспортере быть не должно.

#### 3. `src/state.py` — Хранение состояния

**Отвечает за:**
- Загрузку/сохранение `data/state.json`
- Проверку, был ли пост уже обработан (`is_processed()`)
- Запись о новом отправленном посте (`mark_processed()`)
- Обновление `cutoff_date` (`update_cutoff_date()`)

**Не отвечает за:**
- HTTP-запросы
- Форматирование
- Отправку

#### 4. `src/models.py` — Pydantic-модели

**Отвечает за:**
- Определение структуры конфигурации (`AppConfig`, `SourceConfig`, `MaxChannelConfig`)
- Определение структуры секретов (`Secrets`)
- Валидацию типов и значений

**Не отвечает за:**
- Загрузку конфигов (это делает `config.py`)
- Бизнес-логику

#### 5. `src/config.py` — Загрузка конфигов

**Отвечает за:**
- Чтение `config/settings.yaml`
- Чтение `.env` через `pydantic-settings`
- Возврат объектов `AppConfig` и `Secrets`

**Не отвечает за:**
- Бизнес-логику
- HTTP-запросы

#### 6. `src/main.py` — Оркестрация

**Отвечает за:**
- Загрузку конфигов
- Инициализацию парсера, экспортера, state manager
- Цикл проверки источников
- Обработку сигналов остановки (`Ctrl+C`)
- Закрытие сетевых сессий

**Не отвечает за:**
- Детали парсинга
- Детали отправки
- Детали хранения состояния

### Правила взаимодействия

1. **Парсер → Экспортер:** Парсер возвращает полностью подготовленные данные. Экспортер только форматирует и отправляет.
2. **Экспортер → State:** Экспортер возвращает `message_id`. `main.py` передаёт его в `state.mark_processed()`.
3. **State → Парсер:** `main.py` передаёт `cutoff_date` из state в парсер.
4. **Models → Все:** Модели используются всеми модулями для типизации.

### Последствия для S2-09

Задача **S2-09** (разделение ответственности парсера и экспортера) является **прямым следствием** этого ADR:

1. Удалить `_clean_description()` из `MaxExporter`.
2. Убедиться, что `WordPressParser._format_post()` возвращает полностью очищенный `content`.
3. В `MaxExporter.format_post()` использовать прямой доступ `entry["title"]` вместо `entry.get("title", "")` (S2-10).

## Consequences

**Положительные:**
- Чёткие границы ответственности.
- Нет дублирования кода.
- Легко добавлять новые каналы (только новый exporter, парсер не меняется).
- Легко тестировать (каждый модуль изолирован).

**Отрицательные:**
- Требуется дисциплина: нельзя добавлять логику очистки в экспортер.
- При изменении формата данных нужно обновлять и парсер, и экспортер.

**Что теперь нельзя:**
- Нельзя дублировать `_clean_description()` в парсере и экспортере.
- Нельзя использовать `.get()` в экспортере для маскировки ошибок парсера.
- Нельзя добавлять HTTP-логику в экспортер (только в парсер).
- Нельзя добавлять бизнес-логику в `models.py` или `config.py`.

**Следующий шаг:**
- S2-09: Рефакторинг — разделение ответственности парсера и экспортера.
- S2-10: Заменить `.get()` на прямой доступ с валидацией.

- `0001-project-dump-for-llm-context.md` — исторический дамп.
- Код Этапа 1, кроме точечных правок S2-09 / S2-10.

## Принципы

1. **Один этап — один файл.** Детали — в `0016-stage-2-*.md`, `0017-stage-3-*.md`, и т.д.
2. **Каждая задача имеет ID.** Формат: `S<этап>-<номер>`, например `S2-03`.
3. **Каждая задача ссылается на ADR.** Если задача меняет архитектурное решение — сначала ADR, потом задача.
4. **Критерий завершения этапа — измеримый.** Не «работает», а «`uv run pytest` проходит с покрытием ≥ 80%».
5. **Не усложнять раньше времени.** Celery + Redis — только если APScheduler не справится (Этап 5). Фильтры per-channel — Этап 5, не Этап 3. `asyncio.gather` для каналов — только при 5+ каналах, до этого последовательный цикл.

## Связь с ADR

- ADR фиксируют **решения** (что и почему).
- ROADMAP и stage-файлы фиксируют **работы** (что делать и когда).
- Если задача противоречит ADR — либо задача отменяется, либо пишется новый ADR.

## Принципы

1. **Один этап — один файл.** Детали — в `0016-stage-2-*.md`, `0017-stage-3-*.md`, и т.д.
2. **Каждая задача имеет ID.** Формат: `S<этап>-<номер>`, например `S2-03`.
3. **Каждая задача ссылается на ADR.** Если задача меняет архитектурное решение — сначала ADR, потом задача.
4. **Критерий завершения этапа — измеримый.** Не «работает», а «`uv run pytest` проходит с покрытием ≥ 80%».
5. **Не усложнять раньше времени.** Celery + Redis — только если APScheduler не справится (Этап 5). Фильтры per-channel — Этап 5, не Этап 3. `asyncio.gather` для каналов — только при 5+ каналах, до этого последовательный цикл.

## Связь с ADR

- ADR фиксируют **решения** (что и почему).
- ROADMAP и stage-файлы фиксируют **работы** (что делать и когда).
- Если задача противоречит ADR — либо задача отменяется, либо пишется новый ADR.
