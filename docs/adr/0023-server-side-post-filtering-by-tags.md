# ADR 0023: Серверная фильтрация постов по тегам (`include_tag_ids`)

- **Status:** Accepted
- **Date:** 2026-09-16
- **Related:** ADR 0004 (WP REST API), ADR 0016 (Этап 2, фильтрация), S2-03 (тесты `fetch_posts`)

## Context

В модели `SourceConfig` присутствует поле `include_tag_ids`. Однако в методе `WordPressParser.fetch_posts()` это поле **игнорировалось** при формировании HTTP-запроса к WP API.

При этом аналогичный параметр для категорий (`include_category_ids`) **уже передаётся** на сервер:

```python
if self.source.include_category_ids:
    params["categories"] = ",".join(map(str, self.source.include_category_ids))
```

Для тегов такой строки не было. Как следствие:
- include-правила по тегам **не применялись ни на сервере** (параметр `tags` не передавался), **ни на клиенте** (`_should_exclude()` работает только с `exclude_*`).
- Парсер загружал все посты в пределах `max_pages` и `per_page`, увеличивая трафик и время обработки.
- Возникала асимметрия: `include_category_ids` фильтрует на сервере, `include_tag_ids` — нигде.

## Decision

Добавить параметр `tags` в запрос к WP REST API, если в конфигурации задан непустой `include_tag_ids`. Симметрично уже существующей логике для `include_category_ids`.

**Реализация в `src/parser.py`:**
```python
if self.source.include_tag_ids:
    params["tags"] = ",".join(map(str, self.source.include_tag_ids))
```

### Нюансы поведения WP REST API (принято как данность)
1. **Несколько тегов:** передача `?tags=10,20` работает как логическое **OR**. WP вернёт посты, имеющие *хотя бы один* из указанных тегов.
2. **Комбинация с категориями:** передача `?categories=5&tags=10` работает как логическое **AND**. WP вернёт посты, имеющие *и* категорию 5, *и* тег 10.
3. Мы **не пытаемся** эмулировать сложную клиентскую логику (например, строгий AND по нескольким тегам) и полностью полагаемся на нативное поведение WP REST API.

### Что не меняется
`_should_exclude()` **не изменяется**. Разделение ответственности:
- `include_category_ids`, `include_tag_ids` → серверная фильтрация через параметры запроса.
- `exclude_category_ids`, `exclude_tag_ids` → клиентская фильтрация в `_should_exclude()`.

Это разделение вынужденное: WP REST API не предоставляет параметров `categories_exclude` / `tags_exclude` для `/wp/v2/posts` в ядре.

## Alternatives considered
- **A. Оставить как есть.** Отвергнуто: неэффективно, include-правила по тегам вообще не работали.
- **B. Передавать `?tags=10,20` (выбрано).** Дёшево (2 строки), симметрично категориям, использует нативные возможности WP.
- **C. Использовать `?tag__and=` для строгого AND.** Отвергнуто: недоступно через стандартный REST API без плагинов.
- **D. Кастомный эндпоинт на стороне WP.** Отвергнуто: избыточно для данной задачи.

## Consequences
**Положительные:**
- Сокращение объёма передаваемых данных.
- Ускорение работы парсера.
- Устранение асимметрии с `include_category_ids`.

**Отрицательные:**
- Поведение фильтрации ограничено возможностями WP REST API (OR для нескольких тегов).
- При очень длинных списках `include_tag_ids` возможны проблемы с длиной URL (пока не актуально).

## Связь с задачами
- Изменение связано с **S2-03**: требуется добавить тесты на передачу `?tags=`.

## Done criteria
- Код добавляет `params["tags"]` при непустом `include_tag_ids`.
- Тесты `test_include_tag_ids_parameter` и `test_include_tag_ids_not_sent_when_empty` проходят.
- `_should_exclude()` не изменялся.

## Not to touch
- Клиентская логика `_should_exclude()` для `exclude_tag_ids` остаётся без изменений.
- ADR 0004 не редактируется.
