## Формат ответов

- Как в ADR-файлах: Status / Context / Decision / Tasks /
  Done criteria / Not to touch (где применимо).
- Патчи кода и markdown оборачивать в ЧЕТЫРЕ бэктика снаружи
  (````markdown ... ````). Внутри — обычные тройные для
  вложенных блоков кода.
- Форматтер mdformat с `wrap=80`, `compact_tables=true` —
  не удивляться, что строки переносятся, а таблицы без паддинга.

## Коммиты

Всегда двумя `-m` (заголовок + тело). Одной строкой — без
переноса `\` (Windows Git Bash не переносит `\` через вставку).

Пример:
git commit -m "feat: короткий заголовок" -m "Тело: что, почему, ссылки на ADR."

## Порядок работы

Перед каждым коммитом — полный цикл:
1. uv run ruff check --fix
2. uv run ruff format
3. uv run pytest
4. При необходимости — ручная проверка.

Pre-commit сработает автоматически (ruff, mdformat, sync-with-uv).
Если `Failed` — принять правки, `git add`, повторить.

## Правила из проектных ADR

- ADR 0020: модули по зонам ответственности.
- ADR 0028: любые преобразования данных — только в
  `src/content_transform.py`. Парсер и экспортеры преобразования
  не делают.
- ADR 0029: обрезка `max_length` — эстетическая, мягкая (по словам).
- ADR 0030: источник ≠ канал; репостер связывает их.
- ADR 0031: `?_fields=`, без `_embed`, серверная фильтрация,
  медиа отдельным запросом.

## Правила ведения BACKLOG

- Формат ID: `S<этап>-<номер>`.
- Завершённые этапы — только строка в сводной таблице, без
  отдельного `## Этап N (Done)`.
- История изменений — по датам, каждое событие отдельной строкой.
- Отменённые/устаревшие задачи оставляем в истории (они —
  контекст для будущих решений).

## Что мы не делаем

- Не редактируем старые ADR (кроме явного решения — как с
  0028/0029 при S2g-01a).
- Не трогаем `0001-project-dump-for-llm-context.md` — исторический
  дамп.
- Не пишем код «на будущее» — YAGNI.
