# ADR 0028: Модуль трансформаций и композиция поста

- **Status:** Proposed
- **Date:** 2026-09-18
- **Related:** ADR 0020 (структура модулей), ADR 0012 (модели), ADR 0024 (валидация дат)

## Context

При публикации постов в канал MAX мы используем поле `excerpt.rendered`
из WP REST API. Оно есть всегда, но приходит в HTML:

- обёрнуто в `<p>…</p>`;
- содержит HTML-entities (`&hellip;`, `&#8230;`, `&nbsp;`);
- содержит маркер обрыва `[&hellip;]` в конце, который WordPress
  добавляет, когда сам обрезает анонс;
- может содержать гиперссылки (`<a href="…">текст</a>`).

Отправлять HTML в мессенджер нельзя — читатель увидит теги.
Нужна очистка. Кроме того, сейчас поля поста жёстко закодированы
в шаблоне канала, и если завтра понадобится добавить `subtitle`
или `published` — придётся править код.

Наконец, нет общего правила, где именно делать преобразования
полученных данных. Сейчас очистка живёт в парсере, и при появлении
второго канала её придётся либо дублировать, либо тащить
в неподходящее место.

## Decision

### 1. Источник текста — `excerpt.rendered`

Отказываемся от каких-либо fallback на `content.rendered`.
`excerpt` есть всегда, всегда в HTML, всегда достаточной длины.
Считаем, что текст в пределах разумного — глобальных и канальных
лимитов на этом этапе не вводим.

### 2. Модуль `src/content_transform.py`

Единое место для любых преобразований полученных данных.
Функции-обработчики выбираются по **типу поля**, объявленному
в конфиге. Для каждого типа — свой обработчик.

Обработчики на этом этапе:

- **`html`** — декодирует entities (`&hellip;` → `…`, `&nbsp;` →
  пробел), удаляет HTML-теги (гиперссылки удаляются вместе
  с тегами), удаляет маркер обрыва в конце текста. После
  декодирования маркер выглядит как `[…]` или `[...]`.
  Многоточие на месте маркера **не восстанавливает**. Пробелы
  внутри абзацев схлопываются, границы абзацев (`\n\n`)
  сохраняются.
- **`plain`** — без обработки.

Если для типа, объявленного в конфиге, обработчика нет — падаем
при старте с понятной ошибкой.

### 3. Список полей в `WPRestSourceConfig`

Поля объявляются у каждого источника. Разные типы источников
(WP REST API, RSS для Дзена и т.п.) отдают разные поля. Каждый
элемент содержит имя поля (путь через точку для вложенных,
например `excerpt.rendered`) и его тип.

Класс источника для MVP называется `WPRestSourceConfig` —
явно указывает на тип. Общий родительский класс
(`BaseSourceConfig`) и другие типы (`RssZenSourceConfig`)
появятся, когда будет второй тип источника. Сейчас вводить
их избыточно.

Если шаблон канала ссылается на поле, которого нет ни у одного
активного источника, — падаем при старте. Если поле есть у одного
источника, но отсутствует у другого, пост второго источника
просто пропустит соответствующий блок в шаблоне (см. п. 4).

На уровне списка полей **не задаются ограничения формата канала**.
Если в будущем понадобятся ограничения на уровне поля (например,
защита от гигантских текстов при чтении полного `content`), они
будут отдельным механизмом с отдельной целью — экономия памяти,
а не попадание в формат мессенджера.

### 4. Шаблон канала — список блоков

Шаблон поста задаётся на уровне канала как **список блоков**.
Каждый блок содержит:

- **префикс** — строка, выводимая перед полем;
- **поле** — имя поля из `fields` источника;
- **постфикс** — строка, выводимая после поля;
- **ограничения** — обязательный параметр, специфичный
  для этого места в шаблоне (`max_length`).

Блоки склеиваются в порядке объявления. Если поле блока пустое —
**блок пропускается целиком** (вместе с префиксом и постфиксом).
Если все поля шаблона пусты — пост не публикуется, в лог
пишется `WARNING` с указанием, какие поля были пусты.

Если шаблон канала ссылается на поле, которого нет ни у одного
активного источника, — падаем при старте.

Блок — расширяемая структура. Если позже появятся ограничения,
специфичные для конкретного места в шаблоне, они добавляются
в блок как новые поля. Преобразования при этом остаются
в `content_transform.py` — блок лишь указывает, какое
ограничение применить.

Пример шаблона:

```yaml
template:
  - prefix: ""
    field: title.rendered
    max_length: 55
    postfix: "\n\n"
  - prefix: ""
    field: excerpt.rendered
    max_length: 0  # 0 = без ограничений
    postfix: "\n\n"
  - prefix: ""
    field: link
    max_length: 0
    postfix: ""
```

**Важно:** `max_length` в блоке — это ограничение **формата
канала**. Оно не имеет отношения к ограничениям на уровне
`fields` источника, которые могут появиться позже как защита
ресурсов (например, отсечка гигантских текстов при чтении
полного `content`). Разные цели — разные уровни конфигурации.
Значение `0` означает «без ограничений» — это явный маркер,
что автор конфига подумал и решил не ограничивать поле.

### 5. Валидация конфигурации — отдельный модуль `src/validation.py`

Валидация делится на два уровня.

**Локальные проверки** (не требуют сети) выполняются при старте
основного цикла:

- все поля из шаблонов каналов присутствуют хотя бы у одного
  активного источника;
- для всех типов из `fields` источников есть обработчики
  в `content_transform`.

Эти проверки не зависят от доступности WP и ловят опечатки
в конфиге до начала публикации. Если проверка не проходит —
сервис падает при старте (fail fast). Битый конфиг — это
не временная проблема, а постоянная: результат работы
с таким конфигом непредсказуем.

**Сетевая проверка** (доступность полей в API) выполняется
**вручную** через CLI-утилиту, например:

```
uv run python -m src.validation
```

При старте основного цикла она не запускается, чтобы временная
недоступность WP не блокировала запуск сервиса через systemd.
Если сервис перезапускается, а API в этот момент недоступен —
сервис должен подняться и ждать, а не падать.

CLI-утилита проверяет:

- все поля из шаблонов каналов присутствуют хотя бы у одного
  активного источника;
- для всех типов из `fields` источников есть обработчики;
- каждый источник реально отдаёт свои поля (тестовый запрос
  к API).

Модуль `src/validation.py` используется и при старте
(только локальная часть), и в CLI (полная проверка).
Проектируется так, чтобы позже его можно было вызвать
из веб-интерфейса для проверки конфигурации.

### 6. Правило на будущее

Любое преобразование полученных данных — обрезка, очистка,
приведение типов, извлечение — делается **только**
в `content_transform.py`. Ни парсер, ни экспортер не содержат
логики преобразований. Они вызывают обработчики:

- **парсер** — если преобразование нужно всем каналам;
- **экспортер** — если преобразование специфично для канала.

Это правило фиксируется сейчас, даже если пока в модуле
только два обработчика.

### 7. `_clean_text` удаляется из парсера

Заменяется вызовом обработчика `html` из `content_transform`.
Парсер больше не занимается очисткой текста.

## Задел на будущее

### Текущая модель — плоская

Поля объявляются внутри `WPRestSourceConfig`. Канал один
(`max_channel`). Репостеров как отдельной сущности нет:
`sources` и `export.max_channel` существуют независимо.
Это работает для MVP: один пользователь, один источник,
один канал.

### Целевая модель — двухуровневая

В перспективе — глобальные типы источников и каналов:

- **`source_types`** — глобальные определения типов источников
  (`wp_rest`, `rss_zen`, ...). Поля — свойство **типа** источника,
  а не экземпляра: «WP REST API отдаёт `excerpt.rendered`,
  `title.rendered`, `link`» — это факт про тип, а не про
  конкретный сайт.
- **`channel_types`** — глобальные определения типов каналов
  (`max`, `vk`, ...).
- **Экземпляры у пользователя** — конкретные источники и каналы,
  ссылающиеся на тип. Наследуют поля от типа.
- **`reposters`** — правила: «из источника A постить в каналы
  X, Y с такими правилами фильтрации и шаблоном». Отдельная
  сущность, связывающая источник и каналы.

### Условие перехода

Переход от плоской модели к двухуровневой делается, когда
появится хотя бы одно из:

- второй тип источника (например, RSS для Дзена);
- второй пользователь;
- необходимость в нескольких репостерах у одного пользователя.

До этого — не делаем. YAGNI.

### Что фиксируем сейчас

В MVP-моделях закладываются только те поля, которые нужны
сейчас. `fields` живут в `WPRestSourceConfig`. Уровни
`source_types`, `channel_types` и `reposters` не вводятся.
При появлении одного из триггеров выше — отдельный ADR
на рефакторинг модели.

### Переименование источников

Класс `SourceConfig` переименован в `WPRestSourceConfig` — он
описывает именно источник типа WP REST API (`api_path`,
`featured_image_size`, `include_tag_ids` — специфика WP).
Название `SourceConfig` создавало ложное ожидание, что это
«любой источник».

При появлении второго типа источника (`RssZenSourceConfig`):

- вводится общий родительский класс `BaseSourceConfig`
  с полями `name`, `base_url`, `fields`;
- общие поля переносятся в родителя;
- специфичные остаются в наследниках;
- `SourceConfig` перестаёт использоваться, `WPRestSourceConfig`
  наследует `BaseSourceConfig`.

## Alternatives considered

- **A. Оставить fallback на `content.rendered`.**
  Отвергнуто: `excerpt` есть всегда, fallback — лишнее усложнение.

- **B. Жёстко закодировать поля в шаблоне.**
  Отвергнуто: при добавлении `subtitle` или `published` придётся
  править код.

- **C. Оставить очистку в парсере.**
  Отвергнуто: при появлении второго канала логику придётся
  дублировать или тащить в неподходящее место.

- **D. Regex-правила очистки вынести в конфиг.**
  Отвергнуто: regex — это код. Ошибка в конфиге = тихая порча
  текста; ошибка в коде = упавший тест.

- **E. Fallback при пустом поле — подставлять другое поле.**
  Отвергнуто: пустое поле — норма, а не ошибка. Подстановка
  чужого поля скрывает проблему источника.

- **F. Хранить маркер обрыва `[…]` и заменять его на `…`.**
  Отвергнуто: WordPress сам решает, как помечать обрыв.
  Мы не редактор, не дублируем его работу.

- **G. Валидация при старте, включая сетевую проверку.**
  Отвергнуто: временная недоступность WP не должна блокировать
  запуск сервиса через systemd. Сетевая проверка — только в CLI.

- **H. Заложить `max_length` в `fields` источника.**
  Отвергнуто: разные цели. `max_length` в `fields` — защита
  ресурсов. `max_length` в блоке шаблона — формат канала.
  Смешивание этих механизмов приведёт к путанице: непонятно,
  почему у поля стоит длина 500, если канал просит 200,
  или наоборот.

- **I. Глобальный список полей в `AppConfig`.**
  Отвергнуто: разные типы источников отдают разные поля.
  Глобальный список вынуждал бы либо смешивать поля из разных
  типов, либо вводить per-source переопределения, что усложняет
  модель без выигрыша.

## Consequences

**Положительные:**

- HTML из excerpt не попадает в мессенджер.
- Добавление нового поля — правка конфига, не кода.
- Правило «преобразования — только в `content_transform`»
  снимает вопрос «а где это должно жить?» для всех будущих
  трансформаций.
- Локальная валидация при старте ловит опечатки в конфиге
  до начала цикла.
- Сервис переживает недоступность WP при старте.
- Модуль валидации переиспользуется в веб-интерфейсе (Этап 4).
- Разделение «формат канала» (ограничения в блоке) и «защита
  ресурсов» (потенциальные ограничения в `fields`) зафиксировано
  явно.

**Отрицательные:**

- Тестовый запрос к API при CLI-валидации — лишний HTTP-запрос.
  Приемлемо: запускается вручную, когда меняется конфиг.
- Если WP начнёт отдавать excerpt в другом формате (например,
  plain text вместо HTML), обработчик `html` сработает некорректно.
  Решается добавлением нового типа или переключением типа поля
  в конфиге.
- Список блоков в шаблоне канала менее компактен, чем строка
  с фигурными скобками. Принято ради явной обработки пустых
  полей и явного указания ограничений.
- В шаблоне канала появляется дополнительный уровень
  конфигурации (ограничения в блоках). Принято ради
  явного разделения «формат канала» и «защита ресурсов».
- Битый конфиг при старте приводит к падению сервиса.
  При `Restart=always` в systemd это даст цикл рестартов.
  Смягчается настройками `StartLimitBurst` / `StartLimitIntervalSec`
  в unit-файле (вне рамок этого ADR).
- В MVP-модели поля привязаны к экземпляру источника, а не
  к типу. При появлении второго источника того же типа поля
  придётся дублировать. Принято как компромисс: до появления
  второго типа источника дублирования нет, а рефакторинг
  под двухуровневую модель — отдельная задача
  (см. «Задел на будущее»).
