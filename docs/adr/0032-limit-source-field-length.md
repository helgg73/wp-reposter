# ADR 0032: Ограничение размера полей источника (`FieldSpec.max_length`)

- **Status:** Accepted
- **Date:** 2026-10-07
- **Related:** ADR 0020 (структура модулей), ADR 0028 (модуль трансформаций),
  ADR 0029 (обрезка по `max_length`), ADR 0031 (оптимизация запроса к WP REST
  API)

## Context

### Проблема: гигантские поля после `_fields=`

ADR 0031 убрал `_embed` и ограничил запрос через `?_fields=`, снизив трафик в 8
раз. Но `_fields=` фильтрует **какие** поля тянуть, а не **какого размера**.
Если у поста `content.rendered` весит 5 МБ (бывает у новостных сайтов с длинными
статьями и встроенной вёрсткой), эти 5 МБ:

1. Осядут в памяти как часть `response.json()` — httpx читает весь ответ
   целиком.
1. Пройдут через `_format_post` → `transform_html` — несколько regex-проходов по
   5 МБ строке.
1. Съедят CPU в `re.sub(r"\n{3,}", "\n\n", text)` и `" ".join(p.split())`.

`excerpt.rendered` обычно короткий, но:

- Не все темы заполняют `excerpt` — некоторые отдают полный `content` как анонс.
- Пользователь может объявить `content.rendered` в `source.fields`, чтобы
  постить лид (`truncate_mode: first_paragraph`, ADR 0029).
- Кастомные плагины могут раздувать ответ произвольными полями.

### Разные цели двух `max_length`

В проекте уже есть `PostBlock.max_length` (ADR 0029) — **лимит формата канала**.
Он работает в экспортере, **после** трансформации, чтобы пост влезал в
эстетическое ограничение.

Не хватает **лимита чтения** — защиты ресурсов до того, как гигантский текст
начнёт обрабатываться. Это другая цель, другое место в пайплайне, другой триггер
пересмотра.

### Связь с ADR 0028

ADR 0028, п. 6: «Любое преобразование полученных данных — обрезка, очистка,
приведение типов, извлечение — делается **только** в `content_transform.py`».

ADR 0028, альтернатива H явно разграничила: `max_length` в `fields` источника —
**защита ресурсов**; `max_length` в блоке шаблона — **формат канала**. Смешивать
не нужно. Этот ADR реализует первую половину.

### Связь с ADR 0031

Раздел 6 ADR 0031: «`max_source_field_length` — отдельная задача. Не входит в
этот ADR. См. следующий этап (S2g-02)». BACKLOG, Этап 2g, S2g-02:
«`max_source_field_length` — обрезка больших полей до трансформера».

## Decision

### 1. Поле `max_length` в `FieldSpec`

```python
class FieldSpec(BaseModel):
    name: str
    type: str
    max_length: int | None = None
```

- `None` (по умолчанию) — без ограничений.
- Положительное число — лимит в **символах** на сырое значение поля (до
  трансформации).
- `0` и отрицательные — ошибка валидации (см. п. 5).

### 2. Per-field, не per-source

Лимит живёт у каждого поля, не у источника целиком. Причины:

- Разные поля — разный размер: `link` всегда короткий, `title.rendered` — сотни
  символов, `content.rendered` — десятки-сотни КБ.
- Один лимит на источник либо бесполезен (5000 для `link` — избыточно), либо
  ломает поля (50 для `link` — обрежет ссылку).
- Симметрия с `PostBlock.max_length`: там лимит тоже per-блок, не глобальный.
- Per-field лимит нужен **редко** — только для потенциально гигантских полей.
  `None` по умолчанию означает «не трогать».

### 3. Обрезка — до трансформации, в `_format_post`

Порядок обработки поля:

1. `_get_by_path(post, field.name)` — извлечь сырое значение.
1. **Если `max_length is not None` и значение — строка длиннее лимита —
   обрезать.**
1. `get_transformer(field.type)` → трансформировать.
1. Результат — в `formatted[field.name]`.

Обрезка до трансформера — основная цель: не гонять regex'ы по 5 МБ.

Функция `truncate_raw(text, max_length)` в `src/content_transform.py`:

```python
def truncate_raw(text: str, max_length: int) -> str:
    """Обрезка сырого значения до трансформации (ADR 0032).

    Ресурсная защита, не формат канала. Режет до `max_length`,
    удаляет незавершённый HTML-тег в конце (обрезали mid-tag).
    Многоточие не добавляет — симметрично `truncate` (ADR 0029).

    Не путать с `truncate()` (ADR 0029): тот про формат канала,
    работает после трансформации, поддерживает режимы.
    """
    cut = text[:max_length]
    cut = re.sub(r"<[^>]*$", "", cut)
    return cut
```

### 4. Санитизация незавершённого HTML-тега

Если обрезка попала в середину тега (`<a href="https://examp`), `transform_html`
не удалит незавершённый тег — его regex `<[^>]+>` требует закрывающего `>`. В
посте останется `<a href="https://examp` как текст.

Решение: после обрезки удаляем хвост, начинающийся с `<` без `>`:

```python
re.sub(r"<[^>]*$", "", cut)
```

Одна строка, симметрично философии «мягкой обрезки» ADR 0029: результат может
быть короче лимита, зато без артефактов.

### 5. Валидация: `max_length > 0`, если задан

- `max_length is None` — валидно, без ограничений.
- `max_length >= 1` — валидно.
- `max_length == 0` или `max_length < 0` — ошибка при старте.

Почему `0` — ошибка, а не «без ограничений»:

- В `PostBlock.max_length` (ADR 0028) `0` — вынужденный маркер: Pydantic требует
  значение, автор должен явно подумать. В `FieldSpec` ситуация обратная —
  большинство полей не ограничиваются, `None` естественно выражает «не задано».
- Два разных способа сказать «без ограничений» (`None` и `0`) — источник
  путаницы.
- Явная ошибка на `0` заставляет автора выбрать: либо `None` (без лимита), либо
  положительное число (лимит). Неоднозначности нет.

Проверка — в `validation.py::validate_local`, в проходе по `source.fields`. Это
согласуется с существующим паттерном: `PostBlock.max_length < 0` проверяется там
же, не в Pydantic.

### 6. Не-строковые значения — молча пропускаем

`max_length` осмысленен только для строк. `_get_by_path` может вернуть:

- `str` — применяем лимит.
- `int` (`id`, `featured_media`) — пропускаем.
- `dict` (`title`, если объявлено без `.rendered`) — пропускаем.
- `list` — пропускаем.
- `None` — пропускаем.

Условие: `isinstance(raw_value, str)`. Молча, без WARNING. Обоснование:

- Статически невозможно проверить тип значения — `FieldSpec.type` описывает
  **трансформер**, не тип данных.
- Автор, поставивший `max_length` на `int`-поле, увидит, что пост не обрезан
  (потому что нечего обрезать), и сам поправит конфиг.
- WARNING на каждое `int`-поле в каждом цикле — шум в логах.

Документируем в docstring `FieldSpec` и в `config/settings.example.yaml`.

### 7. Сервисные поля не ограничиваются

Поля `id`, `date`, `guid.rendered`, `featured_media` — служебные, добавляются
парсером автоматически (ADR 0031). `max_length` к ним не применяется:
пользователь не может их объявить в `source.fields` и, следовательно, не может
задать им лимит.

`link` добавляется как служебное **только если не объявлен** в `source.fields`.
Если объявлен — это уже пользовательское поле, `max_length` применится.

### 8. Порядок двух `max_length`

Полный пайплайн поля:

```text
сырое значение (из API)
    ↓
truncate_raw (FieldSpec.max_length)   ← ресурсная защита, ADR 0032
    ↓
transform_html / transform_plain       ← трансформация по типу, ADR 0028
    ↓
truncate (PostBlock.max_length)        ← формат канала, ADR 0029
    ↓
prefix + value + postfix               ← композиция, ADR 0028
```

Оба лимита независимы. Если `FieldSpec.max_length: 20000`,
`PostBlock.max_length: 55`:

- Сырой HTML обрежется до 20000.
- Почистится `transform_html`.
- Финальный текст обрежется до 55 по границе слова.

## Alternatives considered

- **A. Per-source лимит (`WPRestSourceConfig.max_source_field_length`).**
  Отвергнуто: один лимит на все поля — грубо. `link` не нуждается в защите,
  `content.rendered` — да. См. п. 2.

- **B. `int = 0` вместо `int | None = None`.** Отвергнуто: `0` как маркер «без
  ограничений» уместен в `PostBlock` (там автор обязан подумать про каждое поле
  шаблона), но избыточен в `FieldSpec` (большинство полей не ограничивается).
  `None` — идиоматичнее и не вводит двойной семантики. См. п. 5.

- **C. Допускать `0` как «без ограничений» наравне с `None`.** Отвергнуто: два
  способа сказать одно и то же. Валидация запрещает `0`.

- **D. Обрезка по символам без санитизации тега.** Отвергнуто: артефакт
  `<a href="https://examp` в посте. См. п. 4.

- **E. Обрезка по последнему `>` до лимита.** Отвергнуто: может дать результат
  сильно короче лимита, если тег длинный. Санитизация хвоста — дешевле и
  предсказуемее.

- **F. Добавлять многоточие.** Отвергнуто: ADR 0029 уже зафиксировал «многоточие
  не добавляется». Ресурсный лимит — не место для эстетики.

- **G. Обрезка после трансформации.** Отвергнуто: противоречит цели — гигантский
  текст уже прошёл через regex'ы, CPU потрачен.

- **H. Не резать, а падать с ошибкой при превышении.** Отвергнуто: сервис должен
  переживать аномалии источника. Если поле гигантское — обрезаем, не падаем.
  Пост всё равно публикуем.

- **I. Приводить не-строки к строке и резать.** Отвергнуто: меняет тип, ломает
  трансформер (если он ожидает dict/list). См. п. 6.

- **J. Перенести `truncate_raw` в парсер (не в `content_transform`).**
  Отвергнуто: ADR 0028, п. 6 — все текстовые операции в `content_transform`.
  `truncate_raw` — утилита, не обработчик по типу; соседствует с `truncate`.

- **K. WARNING при `max_length` на не-строковом поле.** Отвергнуто: шум в логах.
  См. п. 6.

- **L. Единый `max_length` для источника и шаблона.** Отвергнуто: разные цели,
  разные этапы пайплайна, разные значения. См. п. 8.

- **M. Pydantic-констрейнт `Field(gt=0)` вместо проверки в `validate_local`.**
  Отвергнуто ради консистентности: `PostBlock.max_length` проверяется в
  `validate_local`, там же собираются все ошибки конфига в одном месте.
  Pydantic-констрейнт выбросил бы `ValidationError` раньше и разрозненно.

## Consequences

**Положительные:**

- Гигантские поля обрезаются **до** трансформации — экономия CPU и памяти.
- Защита от кастомных плагинов, раздувающих ответ API.
- Симметрия с `PostBlock.max_length` — единая концепция «лимит в символах» в
  двух местах.
- Не-строки и `None` не ломают пайплайн.
- Санитизация partial-тега предотвращает артефакты в постах.
- `None` по умолчанию — не навязываем лимиты там, где они не нужны.
- Расширение `FieldSpec` — одно опциональное поле, обратно совместимо (старые
  конфиги работают без изменений).

**Отрицательные:**

- В конфиге появляется второе `max_length` (в `FieldSpec` и `PostBlock`),
  семантически разное. Митигация: документировано в обоих docstring и в
  `settings.example.yaml`.
- `0` запрещён — пользователь, привыкший к `PostBlock.max_length: 0`, получит
  ошибку валидации. Митигация: сообщение об ошибке явно объясняет: «используйте
  `None` (без ограничений) или положительное число».
- `truncate_raw` может обрезать HTML mid-tag и «съесть» часть атрибута тега. Это
  осознанный компромисс: санитизация убирает незавершённый тег, но не
  восстанавливает обрезанное содержимое.
- Не-строковые поля молча игнорируются — автор может не заметить, что его лимит
  не работает. Митигация: документировано, тесты покрывают поведение.

**Что теперь нельзя / не нужно:**

- Нельзя задавать `max_length: 0` в `FieldSpec` — ошибка валидации.
- Нельзя ожидать, что `max_length` сработает на не-строковом поле.
- Нельзя резать гигантские поля **после** трансформации — только до.
- Не нужно ставить `max_length` на все поля бездумно — только на потенциально
  гигантские (`content.rendered`, `excerpt.rendered` у нестандартных тем).
- Не нужно путать `FieldSpec.max_length` (ресурсы) и `PostBlock.max_length`
  (формат).

- ADR 0028 — не редактируется. Решение согласуется с п. 6 (все текстовые

  `max_length` в источнике и шаблоне).
- ADR 0029 — не редактируется. `truncate` (формат) и `truncate_raw` (ресурсы) —
  разные функции с разными целями.
- ADR 0031 — не редактируется. Ссылка из раздела 6 реализуется этим ADR.
- `PostBlock.max_length` — не трогаем, поведение не меняется.
- `src/exporters/` — не трогаем. Обрезка сырых значений — не задача экспортеров.
- `src/parser.py::_build_fields_param` — не трогаем. `_fields=` не зависит от
  `max_length`.
