# ADR 0007: Защита от спама через cutoff_date

- **Status:** Accepted
- **Date:** 2026-09-15
- **Related:** ADR 0010 (лимит постов), ADR 0009 (JSON state)

## Context

При первом запуске API может вернуть 50+ старых постов. Если отправить всё сразу — спам в канале. Если лимитировать отправку, но не сдвигать границу времени — старые посты будут приходить снова и снова.

Прямые альтернативы:

1. **Отправлять всё при первом запуске** — спам.
2. **Хранить все GUID и проверять** — состояние разрастается, логика усложняется.
3. **Лимит без cutoff_date** — старые посты приходят повторно.
4. **cutoff_date с движением вперёд** — простая логика, предсказуемое поведение.

## Decision

Использовать **cutoff_date** (дата отсечки) с движением только вперёд во времени.

Как работает:

1. После первого запуска граница = дата **самого нового** отправленного поста.
2. В следующий раз API возвращает только посты новее (`?after=cutoff_date`).
3. Старые посты игнорируются навсегда.

Реализация:

- **Модуль:** `src/state.py` → `StateManager`
  - Поле `last_processed_date: str | None`
  - `_load()` — читает `last_processed_date` из JSON
  - `_save()` — сохраняет `last_processed_date`
  - `update_cutoff_date(date_str)` — обновляет и сохраняет; докстринг: «Обновляет дату отсечки (самый новый пост, который мы взяли в работу)»
- **Модуль:** `src/parser.py` → `WordPressParser.fetch_posts(cutoff_date)`
  - `if cutoff_date: params["after"] = cutoff_date`
- **Модуль:** `src/main.py` → `check_sources()`
  - `state.last_processed_date` передаётся в `parser.fetch_posts()`
  - `newest_sent_date = entry.get("published")` — берётся первый (самый новый) отправленный пост
  - `state.update_cutoff_date(newest_sent_date)`

## Consequences

**Положительные:**

- Гарантия отсутствия спама устаревшим контентом.
- Предсказуемое поведение при первом запуске.
- Простая логика — движение только вперёд.
- Не нужно хранить все GUID для защиты от повторов — cutoff_date отсекает старые посты на стороне API.

**Отрицательные:**

- Посты, не влезшие в лимит при первом запуске, теряются навсегда (принято как feature).
- Если `published` у поста — не дата, а что-то другое (например, `null`), cutoff_date сломается. Нужно будет уточнить на Этапе 2.

**Что теперь нельзя / не нужно:**

- Не нужно проверять все GUID при каждом запросе — API отдаёт только посты новее cutoff_date.
- Не нужно сдвигать cutoff_date назад — только вперёд.
- Не нужно удалять `last_processed_date` из состояния без явного сброса — иначе вернётся «хвост» старых постов.
