# ADR 0036: Общий cutoff репостера при пустом state канала

- **Status:** Accepted
- **Date:** 2026-10-08
- **Related:** ADR 0007 (cutoff_date), ADR 0030 (мультиканальность и модель
  репостера)

## Context

ADR 0030, п. 11 зафиксировал алгоритм вычисления общего cutoff репостера:

```
cutoff = минимальный из cutoff_date всех каналов репостера
```

Цель — не дублировать запросы к WP: парсер вызывается **один раз на репостер**,
cutoff — минимальный из каналов, чтобы отставший канал получил свою историю, а
активные каналы отфильтровали уже обработанное через `state.is_processed(guid)`.

**Баг в реализации.** Формулировка «минимальный из cutoff_date всех каналов» не
покрывает случай, когда у канала нет cutoff. В коде:

```python
cutoffs: list[str] = []
for rc in reposter.channels:
    with StateManager(reposter.name, rc.channel) as state:
        if state.last_processed_date:
            cutoffs.append(state.last_processed_date)
cutoff = min(cutoffs) if cutoffs else None
```

Канал без `last_processed_date` **молча выпадает** из `cutoffs`. Если у одного
канала cutoff есть, а у другого нет (удалён `state.json`, канал добавлен
недавно, миграция), `min(cutoffs)` вычисляется по остальным, и парсер тянет
только посты новее **чужого** cutoff.

**Воспроизводимый сценарий (2026-10-08):**

1. Репостер `og_to_max` с каналами `max_main` и `vk_test`.
1. `max_main.json` есть, `last_processed_date = "2026-10-08T11:43:31"`.
1. `vk_test.json` удалён вручную.
1. Запуск: `cutoffs = ["2026-10-08T11:43:31"]`,
   `cutoff = "2026-10-08T11:43:31"`.
1. Парсер запрашивает посты новее 11:43 — свежих нет.
1. **VK ничего не получает**, потому что постов нет вообще. Отставший канал не
   догоняет историю.

Пользователь ожидает обратного: удаление state одного канала не должно
блокировать этот канал — он должен получить то, что не видел, независимо от
состояния других каналов.

## Decision

Правило вычисления общего cutoff:

- Если **хотя бы у одного** канала `last_processed_date` пуст (None) — общий
  cutoff = **None** (тянем с начала).
- Если у всех каналов cutoff есть — общий cutoff = **минимальный** из них.
- Если каналов нет (теоретически) — cutoff = **None**.

Обоснование: канал без cutoff — «не видел ничего». Тянуть с начала —
единственный способ дать ему историю. Активные каналы при этом не пострадают: их
`state.is_processed(guid)` отфильтрует уже обработанные посты.

### Реализация

Вычисление вынесено в отдельную функцию `compute_reposter_cutoff` в
`src/main.py`. Это позволяет тестировать правило изолированно, без запуска
полного `process_reposter` (который открывает `ReposterLock`, парсит,
экспортирует).

```python
def compute_reposter_cutoff(
    reposter: ReposterConfig,
    base_dir: str = "data/state",
) -> str | None:
    """Вычисляет общий cutoff для репостера (ADR 0030, п. 11 + ADR 0036).

    Возвращает:
    - None, если хотя бы у одного канала cutoff пуст —
      этот канал ещё не видел ничего, тянем с начала;
    - None, если каналов нет;
    - минимальный cutoff_date из всех каналов иначе.
    """
```

## Alternatives considered

- **A. Оставить как есть.** Отвергнуто: баг воспроизводим, нарушает ожидаемое
  поведение «каналы независимы».

- **B. Вызывать парсер отдельно для каждого канала с его cutoff.** Отвергнуто: N
  запросов к WP вместо одного. При 5+ каналах — расточительно. Дублирование
  отфильтровывается `state.is_processed`, ради этого и делали один вызов на
  репостер.

- **C. Использовать максимальный cutoff вместо минимального.** Отвергнуто:
  активный канал, у которого cutoff свежее, «подтянет» отставший канал — и тот
  пропустит посты между своим и чужим cutoff. То же самое, что баг, но с другой
  стороны.

- **D. Пустой cutoff → трактовать как очень старую дату (например,
  `1970-01-01`).** Отвергнуто: магическая константа. `None` — нативный способ
  выразить «без ограничения» в нашем коде (`params["after"]` не добавляется при
  `None`).

- **E. Отдельный cutoff per-channel с отдельным вызовом парсера для каждого.**
  См. B.

## Consequences

**Положительные:**

- Отставший канал получает свою историю независимо от других.
- Удаление `state.json` одного канала — валидный способ «начать заново» только
  для этого канала, не затрагивая остальные.
- Правило явное, легко документируется и тестируется.

**Отрицательные:**

- В редком случае (один канал без cutoff, другие с cutoff) парсер вернёт больше
  постов, чем нужно активным каналам. Лишние отфильтруются `is_processed`, но
  трафик к WP будет выше.
- При `max_posts_per_fetch: 20` и большом расхождении — отставший канал догоняет
  историю **порциями** (по 20 постов за цикл), а не одним залпом. TD-21 в
  BACKLOG.

**Что теперь нельзя / не нужно:**

- Нельзя вычислять общий cutoff как `min()` без проверки на `None` — это
  возвращает баг.
- Не нужно вызывать парсер per-channel — один вызов на репостер остаётся.

- ADR 0030 — не редактируется. Правило п. 11 уточняется этим ADR, не
