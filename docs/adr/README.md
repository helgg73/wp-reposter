# Architecture Decision Records

Этот каталог содержит Architecture Decision Records (ADR) — короткие
заметки о значимых технических решениях проекта: что решили, почему,
и к чему это привело.

## Зачем

ADR фиксируют **контекст** решения, который теряется в коде и
коммитах. Через полгода «почему мы не используем библиотеку X»
восстанавливается за 30 секунд вместо часа археологии по истории
git и переписке.

Отдельная польза — для LLM: если вы даёте модели контекст проекта,
ADR объясняют ограничения и запреты («мы не пишем в прод из тестов»,
«генерированный код не редактируем руками»), которые из кода не видны.

## Формат

Каждый ADR — отдельный файл `NNNN-краткое-название.md`, где `NNNN` —
порядковый номер с ведущими нулями (`0001`, `0002`, ...). Номер
обеспечивает сортировку; дата в имени не нужна, она есть в теле.

Структура файла:

    # ADR NNNN: Краткое название

    - **Status:** Proposed | Accepted | Deprecated | Superseded by [ADR NNNN](...)
    - **Date:** YYYY-MM-DD

    ## Context

    В чём проблема, какие силы действуют, какие альтернативы
    рассматривались. Без воды — только то, что нужно для понимания
    решения.

    ## Decision

    Что именно решили. В утвердительной форме: «используем X»,
    «отказываемся от Y». Одно решение на один ADR.

    ## Consequences

    Что это даёт, какие минусы, что теперь нельзя или не нужно.
    Честно, включая неудобства — иначе ADR теряет смысл.

## Правила

- **Один ADR — одно решение.** Если тянет написать «и ещё мы решили» —
  это второй ADR.
- **ADR не редактируются после принятия.** Изменилось решение —
  пишется новый ADR, старый получает статус `Superseded by [ADR NNNN]`.
  Это журнал, а не документация.
- **Коротко.** Одна страница — предел. Если не влезает, решение
  слишком большое, разбейте на несколько.
- **Без воды.** ADR — не эссе. Контекст, решение, следствия — и всё.
