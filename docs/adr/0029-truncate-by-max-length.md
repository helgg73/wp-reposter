# ADR 0029: Обрезка текста по лимиту `max_length`

- **Status:** Accepted
- **Date:** 2026-09-18
- **Updated:** 2026-10-07
- **Related:** ADR 0028 (модуль трансформаций и композиция поста), ADR 0020 (структура модулей)

## Context

В ADR 0028 введено поле `max_length` в блоках шаблона канала.
Поле парсится и валидируется (проверка «не отрицательный»),
но **не применяется**: текст не обрезается. Это было осознанное
решение — выбор алгоритма обрезки вынесен в отдельную задачу.

Сейчас в примере конфига стоит `max_length: 55` для заголовка,
и это значение молчит. Пора определить алгоритм.

## Природа ограничения

`max_length` — это **эстетическое ограничение**, а не техническое
требование площадки. Мессенджер MAX примет и более длинный текст.
Автор контента сам решает, сколько символов в посте выглядит
хорошо.

Следствия:

- Значение `0` означает «автор решил не ограничивать» — это
  осознанный выбор, а не отключение проверки.
- Валидация проверяет только «не отрицательный». «Разумность»
  значения субъективна и не валидируется.
- Обрезка должна быть мягкой (по словам), а не жёсткой
  (по символам): мы сохраняем читаемость, а не втискиваемся
  в жёсткий лимит.
- Если автор ошибётся с `max_length` и пост получится некрасивым —
  это вопрос вкуса, а не баг. Решается правкой конфига,
  без изменения кода.

Практика покажет, какие значения работают. Если окажется,
что для `excerpt` тоже нужен лимит — добавим `max_length`
в соответствующий блок.

## Decision

### 1. Функция `truncate` в `src/content_transform.py`

Обрезка — это преобразование данных, поэтому живёт в модуле
трансформаций (правило из ADR 0028, п. 6). Это **отдельная
функция**, не обработчик по типу: тип отвечает за формат
(HTML → plain), лимит — за длину. Смешивать не нужно.

### 2. Алгоритм

1. Если `max_length <= 0` — возвращаем текст как есть.
2. Если длина текста не превышает `max_length` — возвращаем
   текст как есть.
3. Разбиваем текст на абзацы по `\n\n`.
4. Идём по абзацам слева направо. Внутри абзаца — по словам.
5. Накапливаем результат, добавляя перед каждым словом
   разделитель: пробел внутри абзаца, `\n\n` на границе абзацев.
6. Как только добавление очередного слова (с разделителем)
   превысило бы `max_length` — останавливаемся, возвращаем
   накопленное.
7. Если первое слово первого абзаца не влезает — возвращаем
   пустую строку.
8. Висящий `\n\n` в конце результата не остаётся: граница
   абзаца добавляется только вместе с первым словом следующего
   абзаца.

Многоточие **не добавляется**. Это согласуется с решением
ADR 0028 не восстанавливать `…` на месте маркера `[…]`.
Читатель видит обрыв по смыслу, а не по символу.

### 3. Порядок применения

Обрезка применяется в **экспортере**, после трансформации поля
по типу и **до** добавления префикса и постфикса блока.
`max_length` относится к самому полю, а не к блоку целиком.

Схема:

1. Парсер извлекает поле, применяет обработчик по типу.
2. Экспортер берёт значение поля.
3. Если `max_length > 0` — применяет `truncate`.
4. Добавляет префикс и постфикс.
5. Склеивает блоки.

### 4. Пустая строка = пропуск блока

Если `truncate` вернула пустую строку (первое слово не влезло),
блок пропускается — как и любой блок с пустым полем
(ADR 0028, п. 4).

### 5. Многострочный текст

Абзацы (`\n\n`) сохраняются. Обрезка идёт по абзацам и словам,
границы абзацев не схлопываются в пробелы. Это важно, если
однажды `max_length` появится у многострочного поля
(например, `excerpt` с лимитом).

## Alternatives considered

- **A. Обрезка по символам (`text[:max_length]`).**
  Отвергнуто: рвёт слова. Природа ограничения — эстетическая,
  а не техническая, значит, важнее сохранить читаемость,
  чем уложиться в точный лимит.

- **B. Обрезка по предложениям.**
  Отвергнуто: алгоритм сложнее (поиск последнего законченного
  предложения, fallback на слово, fallback на символ), а выигрыш
  неочевиден. У `excerpt` от WordPress уже стоит маркер обрыва,
  у `title.rendered` обычно нет точек в середине.

- **C. Добавлять многоточие после обрезки.**
  Отвергнуто: не согласуется с ADR 0028 — там мы решили
  не восстанавливать `…` на месте маркера `[…]`.

- **D. Жёсткая обрезка перового слова, если оно не влезает.**
  Отвергнуто: «Ден…» вместо «Денис» — хуже, чем пропуск блока.
  Пустая строка честнее: слово не влезло — блок не выводим.

- **E. Использовать `textwrap` из стандартной библиотеки.**
  Отвергнуто: `textwrap.wrap` режет по символам с настройкой
  `break_long_words`, но не даёт контроля над абзацами
  и не возвращает «остаток». Проще 15 строк своего кода.

- **F. Обработчик по типу (например, `html_55`).**
  Отвергнуто: тип поля не должен знать про лимит канала.
  Тип отвечает за формат, лимит — за длину.

## Consequences

**Положительные:**

- `max_length` начинает работать: автор конфига управляет длиной
  полей.
- Обрезка мягкая — слова не рвутся, читаемость сохраняется.
- Значение подбирается эмпирически, без привязки к техническим
  лимитам площадки. Если площадка изменит ограничения — конфиг
  не придётся менять.
- Функция `truncate` переиспользуется всеми экспортерами
  (MAX, будущий VK).
- Не добавляется зависимостей: 15 строк чистого Python.

**Отрицательные:**

- Обрезка не гарантирует точное попадание в `max_length`:
  результат может быть короче на длину последнего слова.
  Принято как компромисс ради читаемости.
- Если первое слово не влезает — блок пропускается целиком.
  Для очень коротких `max_length` (например, 5) это может
  привести к пропуску большинства постов. Это ответственность
  автора конфига.
- Многоточие не добавляется, читатель не видит явного признака
  обрыва. Согласуется с ADR 0028.
- Обрезка не учитывает знаки препинания: если в конце осталась
  запятая или двоеточие — они остаются. Мы не редактор.

## Расширение: режим `first_paragraph` (S2e-01)

### Context

`truncate()` в режиме `words` собирает текст по абзацам, пока
влезает в `max_length`. Результат может быть многоабзацным.
Для СМИ логичнее постить только первый абзац (лид).

`truncate_mode` — не про длину, а про то, **что** брать.
`max_length` управляет длиной, `mode` — фрагментом. Это
независимые оси: `max_length = 0` не отменяет режим.

### Decision

Добавлен параметр `truncate_mode: Literal["words", "first_paragraph"]`
в `PostBlock` со значением по умолчанию `"words"`.

Режим `first_paragraph`:
1. Берём только первый абзац (`text.split("\n\n")[0]`).
2. Если `max_length <= 0` — возвращаем весь первый абзац.
3. Если первый абзац ≤ `max_length` — возвращаем как есть.
4. Если длиннее — обрезаем по слову.
5. Остальные абзацы отбрасываем.

### Consequences

**Положительные:**
- Автор конфига выбирает, постить лид или собирать текст
  из нескольких абзацев.
- Обратная совместимость: старые конфиги работают без изменений.

**Отрицательные:**
- Два режима — два пути в `truncate()`. Покрыто тестами.
- `max_length = 0` в режиме `first_paragraph` возвращает
  первый абзац целиком, а не весь текст. Это отличается
  от поведения `words` при `max_length = 0` — легко
  перепутать. Зафиксировано в docstring `truncate`
  и тестами.

### Ограничение: `first_paragraph` зависит от `\n\n` в обработанном поле

`first_paragraph` делит текст по `\n\n`. Это работает
с **обработанным** полем (после `transform_html`), а не
с сырым ответом API.

Что даёт `\n\n` после `transform_html`:

- `content.rendered` — абзацы размечены `<p>...</p>`.
  `transform_html` **заменяет блочные теги на `\n\n`**
  (S2g-01a, ADR 0028) — абзацы сохраняются.
- `excerpt.rendered` — у некоторых тем (например, NewsPaper)
  приходит одним `<p>` без вложенных блочных тегов. После
  `transform_html` — одна строка. `first_paragraph` не даёт
  эффекта.
- `plain`-поля — зависит от источника.

Это **свойство данных**, не баг `truncate` или
`transform_html`. Автор конфига выбирает поле, подходящее
под задачу: для лида — `content.rendered`, для короткого
анонса — `excerpt.rendered`.

### Исправление: блочные теги → `\n\n` в `transform_html` (S2g-01a)

Раньше `transform_html` удалял блочные теги вместе с
остальными, от `</p>\n<p>` оставался один `\n`, нормализация
`\n{3,}` → `\n\n` его не трогала. `content.rendered` после
обработки — одна строка без абзацев, `first_paragraph`
не работал.

Исправлено в S2g-01a: блочные теги (`<p>`, `<div>`) заменяются
на `\n\n` **до** удаления остальных. Детали — в ADR 0028.
